# PI05 异步客户端调参手册

本文记录 `vlash_iner.server.run_pi05_async_client` 在 SO101 真实机器人上的调参结论。目标是让后续 Agent 或开发者不用重新试错，能够快速理解为什么当前参数这样设置，以及下一步应该怎么继续优化。

本文只讨论客户端调参和日志分析。真实上机必须由操作者手动执行，Agent 不要自动运行带 `--confirm-control true` 的命令。

## 背景

当前 PI0.5 异步推理链路分成两部分：

- 服务端：`vlash_iner.server.run_pi05_async_server`
- 客户端：`vlash_iner.server.run_pi05_async_client`

客户端从机器人读取观测，发送到服务端获取一段 action chunk，然后按照 `control_fps` 逐步发送给机器人。为了减少等待，客户端可以在当前 chunk 还没有执行完时提前请求下一段 chunk。

本轮调参关注的问题是：机械臂执行任务 `Put the eraser into the small box` 时，某些时刻会出现本应继续向目标移动、但短暂往回退的现象。这个问题最初怀疑是异步推理导致，但从运行报告看，主要原因不是推理等待，而是 action chunk 切换时新旧 chunk 的动作方向不连续。

## 参数含义

### `--n-action-steps`

表示客户端每次从服务端请求多少步 action。

当前建议：

```text
--n-action-steps 50
```

在 `control_fps=45` 下，一段 chunk 执行时间约为：

```text
50 / 45 = 1.11 秒
```

实验中尝试过 `30` 和 `25`，效果反而更差。原因是 chunk 更短以后切换更频繁，而当前问题正好集中在 chunk 切换处，所以缩短 chunk 会增加边界次数，导致回退更容易被看见。

不推荐：

```text
--n-action-steps 30
--n-action-steps 25
```

除非后续代码增加更强的 chunk continuity correction，否则不要优先缩短这个参数。

### `--inference-overlap-steps`

表示当前 chunk 剩下多少步时，提前请求下一段 chunk。

当前建议：

```text
--inference-overlap-steps 15
```

在 `control_fps=45` 下，提前时间约为：

```text
15 / 45 = 0.333 秒
```

服务端当前 torch 推理通常约 `0.10s` 到 `0.12s`，所以提前 `0.333s` 足够。实验中 `overlap=20` 会重新出现回退，说明提前太久会让下一段 chunk 基于较早的状态规划，等新 chunk 接管时容易产生反向修正。

调参结论：

- `15` 当前最好。
- `20` 太早，有回退。
- `8` 搭配 `future_state_aware=false` 明显变差。
- 可以继续尝试 `13` 或 `14`，但不要盲目增大。

搜索范围：

```text
--inference-overlap-steps 13
--inference-overlap-steps 14
--inference-overlap-steps 15
```

### `--future-state-aware`

表示请求下一段 chunk 时，把当前 chunk 的末尾 action 当作 future state 发给服务端，让服务端预测“接下来”的动作，而不是只基于当前观测重新开始。

当前建议：

```text
--future-state-aware true
```

实验中关闭该参数后，即使使用较大的 blend，回退仍然明显。开启后配合 `overlap=15` 和 `blend=4`，回退基本消失。

当前不要关闭：

```text
--future-state-aware false
```

关闭后下一段 chunk 更容易和上一段动作方向不一致。

### `--chunk-blend-steps`

表示新 chunk 切换后的前几步，用上一帧 action 和新 chunk action 做线性混合。

当前保底建议：

```text
--chunk-blend-steps 4
```

这个值提供了足够的边界平滑，但会带来一点“动作黏”的感觉。

如果想让动作更灵敏，可以按下面顺序试：

```text
--chunk-blend-steps 3
--chunk-blend-steps 2
```

不要认为 blend 越大越好。实验中 `blend=12` 和 `blend=16` 反而更差，因为旧动作残留太久，新 chunk 又在修正轨迹，机械臂会出现被新旧目标来回拉扯的感觉。

不推荐：

```text
--chunk-blend-steps 8
--chunk-blend-steps 12
--chunk-blend-steps 16
```

除非后续任务场景速度更慢，否则这些值容易让动作滞后。

### `--background-inference`

当前建议：

```text
--background-inference true
```

后台线程提前请求下一段 chunk，避免主控制循环阻塞。报告中 `wait_count=0` 说明这部分工作正常。

### `--reuse-observation-within-chunk`

当前建议：

```text
--reuse-observation-within-chunk true
```

这个参数表示只有在需要新 chunk 时才读取新观测，其余 action 步复用最近一次观测。这样可以减少相机和处理器开销，让控制循环更稳定。

注意：这个参数不是模型 prefix cache。它只是客户端观测复用。服务端 torch backend 没有跨请求复用 prefix。

### `--control-fps`

当前建议：

```text
--control-fps 45
```

`control_fps` 决定 action 发送频率。当前上机数据中实际 observed Hz 通常在 `42` 到 `43` 左右，接近目标值。暂时不要因为动作黏而优先提高 `control_fps`，否则可能引入新的控制不稳定。

### `--action-quant-ratio`

当前必须保持：

```text
--action-quant-ratio 1
```

当前客户端代码中 `action_quant_ratio > 1` 被显式禁用。不要用它做降频或平滑。

## 如何读 JSON report

客户端通过 `--output-json` 输出报告。重点看下面字段。

### `wait_count`

如果：

```text
wait_count > 0
```

说明当前 chunk 用完时，下一段 chunk 还没有算好，客户端发生等待。这才是典型异步延迟问题。

本轮实验里：

```text
wait_count = 0
```

所以回退不是推理等待导致。

### `switch_count`

记录新旧 chunk 切换次数。运行时间越长，这个值越大。

### `switch_direction_flip_count`

记录 chunk 切换时，新 action 与上一段实际 action 的方向是否发生反号。

本轮实验中很多配置都是：

```text
switch_direction_flip_count ~= switch_count
```

说明几乎每次切换都存在方向不连续。当前参数只能缓解，不能从模型层面完全消除。

### `max_switch_delta_abs_max`

chunk 切换时，单个 action 维度最大跳变量。越大越可能出现肉眼可见的抽动或回退。

### `max_switch_delta_l2`

chunk 切换时，所有 action 维度整体跳变的 L2 范数。这个指标比单维最大值更能反映整体轨迹是否平滑。

目前相对好的配置约为：

```text
max_switch_delta_l2 ~= 20
```

明显差的配置会到：

```text
max_switch_delta_l2 ~= 50 到 75
```

### `request_latency_s` 和 `server_infer_s`

这两个字段用于判断推理是否足够快。

当前 torch backend p95 通常约：

```text
request_latency_s.p95 ~= 0.115s
server_infer_s.p95 ~= 0.112s
```

在 `control_fps=45` 时，每步约：

```text
1 / 45 = 0.0222s
```

所以 `overlap=15` 提前约 `0.333s`，足够覆盖服务端推理时间。

## 后续优化建议

当前 JSON 只能记录整体 switch delta，不能定位具体哪个 action 维度或哪个关节在回退。如果后续 `blend=3`、`blend=2`、`overlap=13` 仍不能兼顾灵敏和稳定，建议改客户端报告，增加以下字段：

- 每次 chunk switch 的 raw delta 向量。
- 每次 switch 最大 delta 的维度 index。
- action names 与维度 index 的映射。
- 每个维度是否方向反号。
- 混合前 raw action。
- 混合后实际发送 action。

有了这些字段，就能判断回退主要来自哪个关节，例如 shoulder、elbow、wrist 或 gripper。否则只能根据整体指标调参，效率较低。

更进一步可以在代码里实现 continuity correction，而不是只做线性 blend。例如：

- 对新 chunk 起点做 offset alignment，让第一步更接近上一帧实际 action。
- 对特定关节设置边界限速。
- 只对发生反向跳变的维度做平滑，而不是对所有维度统一 blend。
- 记录机器人实际 state 与模型 action 的偏差，用实际 state 而不是上一段 action 推导 future state。

这些属于代码层优化，不是单纯命令行调参。

## 当前结论

当前不要再按“overlap 越大越好”调。更准确的结论是：

```text
overlap 要足够覆盖推理耗时，但不能太早。
```

当前 torch backend 推理 p95 约 `0.11s`，在 `45Hz` 控制频率下：

```text
overlap=15 -> 提前约 0.333s，当前最好
overlap=20 -> 提前约 0.444s，太早，出现回退
```

当前保底配置：

```text
--n-action-steps 50
--inference-overlap-steps 15
--background-inference true
--future-state-aware true
--chunk-blend-steps 4
--reuse-observation-within-chunk true
```

```text
--n-action-steps 50
--inference-overlap-steps 15
--background-inference true
--future-state-aware true
--chunk-blend-steps 3
--reuse-observation-within-chunk true
```
