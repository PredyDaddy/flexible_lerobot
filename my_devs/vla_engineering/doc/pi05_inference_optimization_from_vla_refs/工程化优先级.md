# PI0.5 / VLASH 工程化优先级建议

日期：2026-06-02

相关路径：

- 当前主仓库：`/data/cqy_workspace/flexible_lerobot`
- 当前上机代码：`/data/cqy_workspace/flexible_lerobot/my_devs/`
- VLASH 参考仓库：`/data/cqy_workspace/flexible_lerobot/my_devs/vla_engineering/vlash-main`
- 数据集：`/data/cqy_workspace/flexible_lerobot/datasets/desk_cleanup_v1`
- 上一份分析报告：`my_devs/vla_engineering/doc/pi05_inference_optimization_from_vla_refs/README.md`

## 结论

从工程化优先级看，我建议优先走一条更隔离、更容易验证的路线：

> **先把 VLASH 当成独立训练环境，用已有 `datasets/desk_cleanup_v1` 数据集在 VLASH 内完成训练和推理验证；当前仓库暂时只作为上机部署和机器人控制代码使用。**

这条路线比“立刻把 VLASH 的异步、fusion、训练代码迁移进当前仓库”更稳。原因是：

- VLASH 本身已经围绕 PI0.5 训练、LoRA、异步推理、shared observation、action quantization 做了一整套配置和入口。
- 当前仓库已经承担机器人上机、设备、相机、控制循环等工程职责，直接把 VLASH 模型训练系统迁进去，会让训练、推理、上机三个边界缠在一起。
- 你现在已经有 `datasets/desk_cleanup_v1`，最短验证路径不是先迁移代码，而是先证明：**VLASH 能不能用这份数据训出一个可用 PI0.5 checkpoint，并且这个 checkpoint 能不能被当前上机代码消费。**

所以优先级应该从“代码迁移”切换成“链路打通”。

## 两种路线对比

### 路线 A：把 VLASH 能力迁移进当前仓库

这条路线是之前报告里说的：

1. 当前仓库做 baseline profiler。
2. 启用 bf16、`torch.compile`、warmup。
3. 迁移 VLASH 异步 action chunk runtime。
4. 再做 action quantization。
5. 最后验证 QKV/MLP fusion。

优点：

- 最终所有能力都在当前仓库中，长期维护统一。
- 当前上机代码和 PI0.5 policy 之间接口最直接。
- 对机器人运行时适配最可控。

缺点：

- 前期工程量大。
- 每一步都要处理当前 LeRobot PI0.5 和 VLASH PI0.5 的结构差异。
- 很容易陷入“还没训练好，就开始改推理；还没推理稳，就开始改上机”的混乱。
- QKV/MLP fusion、VLASH policy、LoRA checkpoint merge 等逻辑迁移风险比较高。

适合场景：

- 已经证明 VLASH 训练出来的模型对 `desk_cleanup_v1` 有效果。
- 已经明确当前仓库上机推理瓶颈确实需要这些优化。
- 需要长期把所有训练/部署逻辑收敛到一个仓库。

### 路线 B：VLASH 隔离训练，当前仓库只负责上机

这条路线是你刚才提出的思路：

1. 在 `vlash-main` 内单独建环境。
2. 用 `datasets/desk_cleanup_v1` 在 VLASH 里训练 PI0.5。
3. 在 VLASH 里先完成离线 eval / mock inference / latency benchmark。
4. 导出或整理 checkpoint。
5. 当前仓库只加载这个 checkpoint 做上机部署。

优点：

- 训练环境和上机环境隔离，问题定位更干净。
- 可以先利用 VLASH 已有训练能力，不急着迁移代码。
- 当前仓库不会被训练框架、LoRA、QLoRA、shared observation 等逻辑污染。
- 如果 VLASH 训练效果不好，可以快速止损，不影响当前主仓库。
- 如果 VLASH 训练效果好，再决定是“只消费 checkpoint”还是“迁移关键能力”。

缺点：

- 需要解决 VLASH checkpoint 和当前仓库 PI0.5 加载格式的兼容问题。
- VLASH 的 normalization 默认和当前 LeRobot PI0.5 可能不同，需要严格对齐。
- VLASH policy 可能带有自己的 config、state prompt、LoRA merge 和 model key mapping，需要确认当前上机代码能否直接加载。
- 如果最终要用 VLASH 的 async runtime，而不是只用 checkpoint，仍然要做运行时接口适配。

适合场景：

- 你已经有数据，想尽快验证 `desk_cleanup_v1` 能不能训出有效策略。
- 当前主仓库已经能上机，不想先大改。
- 你想把训练问题和上机问题拆开。

## 推荐工程优先级

我建议当前阶段采用：

> **路线 B 优先，路线 A 后置。**

也就是：

1. 先不迁移 VLASH 代码到当前仓库。
2. 先在 VLASH 内独立训练 `desk_cleanup_v1`。
3. 训练可用后，再验证 checkpoint 能否接入当前仓库上机。
4. 只有当 checkpoint 有效果，并且上机 latency 不满足需求时，再迁移 VLASH 的异步 runtime / compile warmup / action quantization。
5. QKV/MLP fusion 继续后置，作为模型内部专项优化。

## 建议执行顺序

### P0：确认数据集能被 VLASH 读取

目标：先确认 `datasets/desk_cleanup_v1` 能否作为 VLASH 训练输入。

检查项：

- 数据集是否是 LeRobot dataset 格式。
- 是否有 `meta/info.json`、episodes、video 或 image 数据。
- feature 名称是否匹配 VLASH / LeRobot 预期：
  - `observation.images.*`
  - `observation.state`
  - `action`
  - `task`
- camera 名称是否和未来上机 robot camera 名称一致。
- state/action 维度是否和当前机器人一致。
- fps、chunk_size、n_action_steps 是否合理。

如果这里不通过，先不要训练。

### P1：在 VLASH 内建立独立训练环境

目标：让 VLASH 能自己跑起来，而不是先改当前主仓库。

建议：

- 新建独立 conda 环境，例如 `vlash_pi05` 或 `vlash_desk_cleanup`。
- 在 `vlash-main` 内执行 editable install。
- 保留当前仓库的 `lerobot_flex` 作为上机/分析环境，不要混用。
- 所有训练日志、checkpoint、wandb/rerun 输出都放在 VLASH 自己的 outputs 下。

注意：

- 这一步是少数可以不用 `lerobot_flex` 的地方，因为它是隔离训练环境本身；但如果由 Codex 执行当前仓库命令，仍应遵守当前仓库约束使用 `lerobot_flex`。
- 训练环境和上机环境分开后，要明确记录依赖版本，否则后面 checkpoint 转换会难排查。

### P2：基于 VLASH PI0.5 配置训练 `desk_cleanup_v1`

目标：先得到一个 VLASH 训练出的 PI0.5 checkpoint。

建议从 VLASH 示例开始改：

- `vlash-main/examples/train/pi05/sync.yaml`
- `vlash-main/examples/train/pi05/async.yaml`
- `vlash-main/examples/train/pi05/async_lora.yaml`

优先顺序：

1. 先跑最小训练 smoke test。
2. 再跑 LoRA 或 async 训练。
3. 再考虑 shared observation 或 QLoRA。

不建议一开始就开太多功能：

- async
- LoRA
- shared observation
- QLoRA
- compile
- fusion

第一版应该先证明数据集、processor、normalization、checkpoint 保存都没问题。

### P3：在 VLASH 内做离线推理和 latency benchmark

目标：不要马上上机，先离线确认 checkpoint 能推理。

检查项：

- 同一个 episode 里抽若干 observation，跑 `predict_action_chunk`。
- action shape 是否正确。
- action 数值是否在合理范围。
- normalization / unnormalization 是否正确。
- 推理 latency 是否稳定。
- 是否能在 mock robot 或 replay 环境里跑通。

如果 VLASH 自己离线推理都不稳定，不要接当前主仓库上机。

### P4：验证 checkpoint 能否被当前仓库消费

目标：决定“当前仓库只作为上机代码”是否成立。

这里有两个可能结果。

结果 1：当前仓库 PI0.5 能直接加载 VLASH checkpoint。

这是最理想的。当前仓库只需要：

- 加载 checkpoint。
- 使用当前 preprocessor / postprocessor。
- 按当前 robot interface 上机。

结果 2：不能直接加载。

这也很正常，因为 VLASH 的 PI0.5 有自己的 key mapping、config、normalization 和可能的 LoRA merge 逻辑。

此时有两个选择：

- 写 checkpoint 转换方案，把 VLASH checkpoint 转成当前 LeRobot PI0.5 可加载格式。
- 或者当前仓库上机时引入 VLASH policy loader，但只作为隔离模块，不把训练代码整体迁进来。

优先建议：

> **先尝试 checkpoint 转换，不要一开始就把 VLASH policy 全量引入当前上机代码。**

### P5：当前仓库上机验证

目标：当前仓库只负责机器人运行时。

当前仓库需要做的是：

- camera / state / action feature 对齐。
- policy checkpoint 加载。
- preprocessor / postprocessor 对齐。
- action chunk 执行。
- 安全限位、急停、日志。

此时先不要迁移 VLASH 的异步 runtime。先用当前同步或已有 chunk 队列跑一次上机 smoke test。

通过后再做：

- compile warmup
- bf16
- async overlap
- RTC / future-state-aware
- action quantization

## 当前最推荐的落地路线

我建议按下面这个顺序推进：

1. **VLASH 数据集适配检查**

   确认 `datasets/desk_cleanup_v1` 能被 VLASH 训练脚本读取。

2. **VLASH 最小训练 smoke test**

   用很小 step 数跑通训练，不追求效果。

3. **VLASH 正式 LoRA / async 训练**

   得到一个 checkpoint。

4. **VLASH 离线推理验证**

   确认 checkpoint action shape、数值范围、latency。

5. **checkpoint 接入当前仓库验证**

   先尝试当前 PI0.5 loader；不行再做转换或隔离 loader。

6. **当前仓库上机 smoke test**

   先同步执行，不开异步。

7. **当前仓库推理优化**

   按顺序启用：

   - bf16
   - `torch.compile` + warmup
   - VLASH 式 async chunk scheduler
   - action quantization
   - QKV/MLP fusion

## 为什么不建议一开始迁移 VLASH 异步代码

因为你现在的最大未知不是“异步代码能不能写”，而是：

- `desk_cleanup_v1` 能不能被 VLASH 正确训练。
- VLASH 训练出的 PI0.5 checkpoint 对任务是否有效。
- 这个 checkpoint 能不能被当前上机代码消费。
- normalization、state prompt、camera/action features 是否一致。

如果这些还没确定，就先迁移异步 runtime，容易出现一种情况：

> 上机失败了，但不知道是数据集、训练、checkpoint、processor、normalization、异步调度、future state 还是机器人接口的问题。

工程上应该先减少变量。

## 关键风险

### 风险 1：VLASH checkpoint 与当前 PI0.5 loader 不兼容

VLASH 的 `vlash/policies/pi05/modeling_pi05.py` 有自己的 key mapping 和模型包装。当前 LeRobot PI0.5 的 `from_pretrained` 也有自己的 key remapping。

应对：

- 先做 checkpoint load dry-run。
- 记录 missing keys / unexpected keys。
- 必要时做转换文档，而不是直接改模型代码。

### 风险 2：normalization 不一致

当前 LeRobot PI0.5 默认配置使用 quantiles；VLASH 示例配置里倾向使用 mean/std。

应对：

- 明确训练 checkpoint 的 normalization stats。
- 上机时必须使用训练时同一份 stats。
- 不要用当前仓库默认 stats 去跑 VLASH 训练出的 checkpoint。

### 风险 3：state prompt 语义不一致

当前 LeRobot PI0.5 processor 会把 normalized state 离散化后拼进 prompt。

VLASH PI0.5 也有 state prompt / state conditioning 逻辑，但配置可能不同。

应对：

- 训练和部署必须使用同一种 state 表达。
- 如果 VLASH 使用 `state_cond=True` 或不同 prompt 格式，当前仓库直接加载可能行为不一致。

### 风险 4：camera/action feature 名称不一致

训练数据里的 camera 名称必须和上机 robot camera 名称一致，或者要有明确 rename map。

应对：

- 在训练前固定 feature 命名。
- 上机前做 camera/action schema 对齐表。

### 风险 5：异步调度掩盖模型问题

异步会让机器人看起来更流畅，但也会让错误传播更快。

应对：

- 第一次上机必须同步或低速。
- action chunk 正常后再开 async overlap。

## 决策点

### 决策点 1：VLASH 能否读 `desk_cleanup_v1`

如果不能读：

- 先做数据集适配。
- 不进入训练。

如果能读：

- 进入最小训练 smoke test。

### 决策点 2：VLASH checkpoint 是否有效

如果离线推理 action 明显异常：

- 回到数据、normalization、config 检查。

如果离线推理正常：

- 验证当前仓库加载。

### 决策点 3：当前仓库能否加载 VLASH checkpoint

如果能直接加载：

- 当前仓库继续只做上机。

如果不能直接加载：

- 优先做 checkpoint 转换。
- 转换成本过高时，再考虑引入 VLASH policy loader。

### 决策点 4：上机 latency 是否满足需求

如果同步上机已经满足：

- 暂时不迁移异步 runtime。

如果不满足：

- 再迁移 VLASH 异步 runtime。
- 然后再考虑 action quantization / fusion。

## 最终建议

当前我更推荐你的新想法：

> **把 VLASH 作为隔离训练仓库，用 `datasets/desk_cleanup_v1` 先训练出 checkpoint；当前仓库先只作为机器人上机代码。**

这比立刻迁移 VLASH 代码更符合工程优先级。

真正需要迁移的不是一整套 VLASH，而是按验证结果逐步迁移：

1. checkpoint 格式或 loader 适配。
2. compile warmup / bf16 运行配置。
3. async chunk scheduler。
4. action quantization。
5. QKV/MLP fusion。

也就是说，当前阶段的第一目标不是“迁移 VLASH”，而是：

> **让 VLASH 训练链路和当前仓库上机链路通过 checkpoint 这个边界解耦。**

只要这个边界打通，后面迁移什么、不迁移什么，就会清楚很多。
