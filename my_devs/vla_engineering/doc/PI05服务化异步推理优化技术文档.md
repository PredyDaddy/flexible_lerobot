## 结论

当前 PI0.5 推理优化做得好的核心原因不是单点优化，而是把三类优化组合到了一起：

```text
服务端模型常驻
  + torch.compile 预编译和 warmup
  + action chunk 异步 overlap 执行
  + 客户端只负责采集 observation 和执行机器人
```

这套结构把原本阻塞机器人执行的模型推理时间拆出来，并尽量藏到当前 action chunk 的执行时间里。

实测结果：

```text
torch.compile 冷编译 + warmup 总耗时：约 95.38s
第一次 warmup：约 93.55s
compile 后稳定推理：约 52-68ms / 50-step action chunk
compile 后稳定平均：约 56ms / chunk
不开 compile 稳定推理：约 97ms / chunk
compile 稳定推理加速比：约 1.7x
compile 后单 chunk 延迟降低：约 42%
```

机器人服务化异步运行实测日志：

```text
request_latency=0.067s
server_infer=0.060s
wait_count=0
```

这说明本机服务化链路中，端到端请求约 67ms，服务端模型推理约 60ms，HTTP/pickle 额外开销约 7ms，并且客户端没有因为下一段 action chunk 未返回而等待。

## 总体架构

服务化以后，系统分成两端：

```text
客户端：机器人侧
  - 连接 SO101/SO100 follower
  - 采集 top/wrist camera 和 robot state
  - 构造 LeRobot observation frame
  - 通过 HTTP 把 observation 发给服务端
  - 接收 action chunk
  - 使用 AsyncChunkManager 管理 chunk 执行和 overlap
  - 做 action safety check
  - 下发 robot action

服务端：模型侧
  - 加载 PI0.5 checkpoint
  - 加载 checkpoint 自带 preprocessor/postprocessor
  - 可选 torch.compile
  - 可选 warmup
  - 接收客户端 observation
  - 执行 policy.predict_action_chunk(...)
  - 返回 action chunk
```

核心数据流：

```text
robot.get_observation()
  -> robot_observation_processor(...)
  -> build_dataset_frame(...)
  -> HTTP POST /infer
  -> prepare_observation_for_inference(...)
  -> policy preprocessor
  -> PI0.5 predict_action_chunk(...)
  -> policy postprocessor
  -> action chunk
  -> AsyncChunkManager.get_action(...)
  -> make_robot_action(...)
  -> robot_action_processor(...)
  -> robot.send_action(...)
```

服务端只做推理，不管理机器人执行状态；客户端管理控制节奏、chunk 切换和安全检查。这样后续把服务端迁移到另一台 GPU 机器时，只需要把客户端的 `--server-url` 改成远端 IP。

## 为什么服务化有价值

原始本地推理通常是：

```text
机器人采集 observation
  -> 本地模型推理
  -> 机器人执行 action
```

这种方式的问题是模型推理和机器人执行在同一个主循环里互相阻塞。模型慢时，机器人控制循环也慢。

服务化后变成：

```text
机器人客户端负责实时执行
模型服务端负责 action chunk 推理
```

优势：

- 模型常驻服务端，避免每次客户端启动都重新加载模型。
- GPU 推理和机器人 I/O 分离，便于把模型放到更强的机器。
- 客户端可以在执行当前 action chunk 时提前请求下一段 chunk。
- 端到端延迟可以通过日志拆分为 `request_latency` 和 `server_infer`，便于定位瓶颈。
- 后续可继续替换服务端 backend，例如 TensorRT、Triton、CUDA Graph，而客户端机器人执行逻辑不需要大改。

## 异步加速原理

PI0.5 的推理接口可以一次返回一段 action：

```text
action_chunk shape = [1, 50, 6]
```

也就是说，一次模型推理不是只返回下一步 action，而是返回 50 步 action。

这给异步执行提供了空间：

```text
先请求一个 action chunk
机器人按 control-fps 一步步执行 chunk
当前 chunk 快执行完时，后台请求下一段 chunk
下一段 chunk 提前返回后，客户端无缝切换
```

这个过程的本质是：

```text
用当前 chunk 剩余执行时间覆盖下一次模型推理时间
```

也就是 overlap。

### 同步模式

如果关闭 overlap：

```bash
--inference-overlap-steps 0
--background-inference false
```

执行方式是：

```text
请求 chunk 1
等待服务端返回
执行 chunk 1
chunk 1 执行完
请求 chunk 2
等待服务端返回
执行 chunk 2
```

问题是 chunk 边界容易出现等待。机器人可能表现为：

```text
动一段
停一下
再动一段
```

### 异步 overlap 模式

如果打开：

```bash
--inference-overlap-steps 8
--background-inference true
```

执行方式变成：

```text
请求 chunk 1
等待服务端返回
执行 chunk 1

chunk 1 执行到还剩 8 步
后台请求 chunk 2

继续执行 chunk 1 剩余 8 步

如果 chunk 2 已经返回
直接切换到 chunk 2

chunk 2 执行到还剩 8 步
后台请求 chunk 3
```

只要服务端在 overlap 预留时间内返回，机器人就不会在 chunk 边界等待。

## AsyncChunkManager 状态机

`AsyncChunkManager` 是客户端异步 runtime 的核心。

关键状态：

```text
current_chunk
  当前正在执行的 action chunk

next_chunk
  已经推理完成、等待切换的下一段 action chunk

next_future
  后台线程中正在请求的下一段 action chunk

chunk_index
  当前 chunk 已经执行到第几步

previous_action
  上一次实际输出的 action，用于 chunk blend

stats
  记录 request/inference 次数、最近耗时、pending 状态和 wait_count
```

核心流程：

```text
1. 如果没有 current_chunk，先同步请求第一段 chunk。
2. 每次 get_action(...) 返回 current_chunk[chunk_index]。
3. chunk_index 前进一位。
4. 如果 chunk_index 到达 n_action_steps - overlap_steps，启动下一次推理。
5. 如果 background_inference=true，下一次推理放到后台线程。
6. 当前 chunk 执行完后，如果 next_chunk 已经准备好，立即切换。
7. 如果 next_chunk 未准备好，等待 future 完成，并增加 wait_count。
```

`wait_count` 是判断异步是否成功的关键指标：

```text
wait_count = 0
  说明 chunk 边界没有等待，服务端推理跟得上。

wait_count 持续增加
  说明当前 chunk 执行完时下一段还没返回，机器人被迫等模型。
```

## 三个核心调参项

推荐主力参数：

```text
control-fps 45 / overlap 8 / blend 2
```

稍快一点或更抗延迟参数：

```text
control-fps 45 / overlap 10 / blend 2
```

### control-fps

`control-fps` 控制客户端下发 action 的频率。

```bash
--control-fps 45
```

表示机器人每秒执行约 45 个 action step。

换算成单步时间：

```text
1 / 45 = 0.0222s
```

也就是每 22.2ms 下发一次 action。

`control-fps` 提高后，机器人动作会更紧凑，但当前 chunk 也会更快被消耗。如果服务端推理赶不上，就会导致 `wait_count` 增加。

### overlap

`overlap` 对应参数：

```bash
--inference-overlap-steps 8
```

含义是：

```text
当前 action chunk 还剩 8 步时，就提前请求下一段 action chunk。
```

如果：

```text
control-fps = 45
overlap = 8
```

则服务端可用的提前时间是：

```text
8 / 45 = 0.1778s
```

也就是约 178ms。

如果：

```text
overlap = 10
```

则提前时间是：

```text
10 / 45 = 0.2222s
```

也就是约 222ms。

根据实测：

```text
request_latency = 67ms
server_infer = 60ms
```

所以 `overlap=8` 已经有较大余量：

```text
178ms - 67ms = 111ms
```

`overlap=10` 余量更大：

```text
222ms - 67ms = 155ms
```

但是 overlap 不是越大越好。overlap 太大意味着下一段 chunk 更早基于旧 observation 生成，可能降低闭环反馈的实时性。因此当前主力建议是 `overlap=8`，只有当 `request_latency` 抖动较大或 `wait_count` 增加时再尝试 `overlap=10`。

### blend

`blend` 对应参数：

```bash
--chunk-blend-steps 2
```

它不是提速参数，而是平滑参数。

因为 chunk 切换时可能出现：

```text
上一个 chunk 最后一步 action 与新 chunk 第一步 action 差异较大
```

这会导致机械臂突然跳一下。

`blend=2` 表示新 chunk 前两步做平滑过渡：

```text
第 0 步：更偏向上一帧 action
第 1 步：更偏向新 chunk action
第 2 步开始：完全使用新 chunk action
```

代码逻辑：

```python
alpha = (chunk_index + 1) / (blend_steps + 1)
blended_action = (1.0 - alpha) * previous_action + alpha * action
```

`blend=2` 是一个比较稳的默认值。太小可能 chunk 切换顿挫，太大可能让动作变钝。

## reuse-observation-within-chunk

参数：

```bash
--reuse-observation-within-chunk true
```

含义：

```text
只有需要请求新 action chunk 时才重新读取 observation。
chunk 内执行 action 时，不每一步都重新读相机和重建 observation。
```

这能减少客户端压力：

- 降低相机读取频率。
- 降低 CPU 图像处理和 processor 开销。
- 更容易让 robot action loop 稳定在 45Hz。

副作用：

```text
chunk 内视觉反馈不是每一步更新。
```

因此它适合当前这种 action chunk 时间较短、并且任务对 1 秒内视觉反馈变化不极端敏感的场景。

如果机器人动作质量出现明显闭环滞后，可以尝试关闭：

```bash
--reuse-observation-within-chunk false
```

但关闭后客户端相机和 observation 处理压力会上升。

## torch.compile 优化原理

`torch.compile` 的作用不是生成一个固定 TensorRT engine，而是在 PyTorch 运行时捕获可图化的 tensor 计算，并交给 Dynamo/AOTAutograd/Inductor 做图优化和 kernel 生成。

它并不一定编译整个程序：

```text
prepare_observation_for_inference
  多数是 Python/dict/processor 逻辑，不一定被完整编译

policy preprocessor/postprocessor
  包含 pipeline 和转换逻辑，也不一定完整编译

policy.predict_action_chunk
  其中的 PyTorch module 前向计算是主要 compile 受益部分
```

所以 `torch.compile` 更准确的理解是：

```text
编译模型内部可捕获的 tensor 计算图
减少 Python overhead
做部分算子融合和 kernel 优化
对固定 shape 的重复推理尤其有效
```

当前服务端非常适合 `torch.compile`：

- 服务端常驻。
- batch size 固定为 1。
- top/wrist image shape 固定为 480x640。
- state dim 固定为 6。
- action chunk size 固定为 50。
- task 基本固定。
- 每次请求重复调用同一套 PI0.5 chunk 推理路径。

这类固定 shape、重复调用的在线推理，是 `torch.compile` 的理想使用场景。

## 为什么这套系统能够做得这么好

### 1. 一次推理返回一个 action chunk

如果模型每次只返回 1 步 action，那么每个控制 step 都必须等待模型。PI0.5 当前一次返回 50 步 action，这让客户端可以缓存未来动作。

这就是异步执行的基础。

### 2. overlap 把推理时间藏进执行时间

在 `control-fps=45`、`overlap=8` 时，客户端给下一次推理预留约 178ms。

当前服务端端到端请求约 67ms，因此下一段 chunk 能在当前 chunk 执行完之前返回。

所以机器人不会等模型。

### 3. torch.compile 把单 chunk 推理压到约 56ms

不开 compile 时稳定推理约 97ms。compile 后约 56ms。

这个优化给 overlap 留出更大余量：

```text
overlap=8 @ 45Hz 预留时间：178ms
不开 compile 推理：约 97ms
开 compile 推理：约 56ms
```

compile 后更适合远端服务器，因为网络抖动和序列化开销还有额外空间。

### 4. 服务端常驻摊薄 compile 成本

冷编译需要约 95s。如果每次机器人执行都重新启动服务端，这个成本很高。

但当前架构是：

```text
服务端启动一次
模型常驻
compile/warmup 一次
客户端可以反复启动、停止、调参
```

因此 compile 成本被服务端生命周期摊薄。

### 5. 客户端和服务端职责清晰

服务端只做模型推理，客户端只做机器人控制。

这让系统容易扩展：

```text
本机服务端
  -> 远端 GPU 服务端
  -> 更强服务端 backend
  -> TensorRT/Triton 专项优化
```

客户端执行逻辑不需要随服务端 backend 大改。

### 6. pickle/numpy 协议避免图片 base64 开销

当前本机服务化使用：

```text
FastAPI + pickle + requests.Session
```

observation 里直接传 numpy array，避免 JSON/base64 的图像编码开销。

实测：

```text
request_latency - server_infer = 67ms - 60ms = 7ms
```

本机额外协议开销很小。

### 7. 固定 shape 降低动态重编译风险

当前输入固定：

```text
batch size = 1
top image = 480x640
wrist image = 480x640
state dim = 6
chunk size = 50
```

固定 shape 对 `torch.compile` 和稳定推理都非常重要，可以减少重新 trace 或重新 compile 的风险。

## 日志解读

客户端核心日志：

```text
request_latency=0.067s
server_infer=0.060s
request_count=25
pending=False
wait_count=0
```

含义：

```text
request_latency
  客户端一次 HTTP 请求总耗时，包括网络、序列化、服务端推理和响应返回。

server_infer
  服务端内部推理耗时。

request_count
  已经请求了多少个 action chunk。

pending
  是否有后台请求还没有返回。

wait_count
  当前 chunk 用完时是否因为下一段 chunk 未返回而等待。
```

判断标准：

```text
wait_count = 0
  最理想，说明 overlap 足够。

request_latency < overlap_steps / control_fps
  通常可以无缝切 chunk。

server_infer 接近 request_latency
  说明主要耗时在模型推理。

request_latency - server_infer 很大
  说明网络、序列化或服务端排队开销较大。
```

## 风险和边界

### future-state-aware 不是纯性能参数

`future-state-aware` 会用当前 chunk 末尾 action 替换下一次推理的 state。

这不是单纯加速，会改变模型输入语义。PI0.5 的 state 可能经过 processor/tokenizer 进入模型，因此 future state 是否合理需要单独 A/B 测试。

建议：

```text
先关闭 future-state-aware 跑稳。
再单独打开做对照。
```

### overlap 不能无限加大

overlap 太大意味着下一段 chunk 更早基于旧 observation 推理，闭环反馈会变弱。

当前建议：

```text
主力 overlap=8
抗抖动 overlap=10
不要一开始设置过大
```

### compile 冷启动成本高

冷编译约 95s。短时间实验不开 compile 也能跑，但正式调性能和远端部署建议开 compile。

正确使用方式：

```text
服务端启动一次
完成 compile/warmup
保持服务端常驻
客户端反复运行和调参
```

### 远端部署时网络会成为新变量

本机协议开销约 7ms。远端后可能增加：

- 网络传输延迟。
- 图片数据传输开销。
- 服务端排队。
- 防火墙或网卡抖动。

远端联调时需要重点观察：

```text
request_latency - server_infer
wait_count
```

如果差值变大，需要考虑：

- 更早 overlap。
- 图像压缩协议。
- 更快网络。
- 服务端多进程或请求队列优化。
- 更专门的 RPC 协议。

- 评估服务端批处理或多机器人请求场景。

## 总结

这套 PI0.5 服务化异步推理之所以表现好，是因为它同时解决了三个层面的问题：

```text
模型层：
  torch.compile 将单 chunk 推理从约 97ms 降到约 56ms。

调度层：
  AsyncChunkManager 用 overlap 把下一次推理藏到当前 chunk 剩余执行时间里。

系统层：
  服务端常驻模型，客户端专注机器人控制，HTTP/pickle 协议开销小，本机请求额外开销约 7ms。
```

因此当前主力配置：

```text
control-fps 45 / overlap 8 / blend 2
```

可以在服务端 `server_infer` 约 60ms 的情况下稳定运行，并保持：

```text
wait_count=0
```

这说明当前优化已经不是单纯“模型跑得快”，而是整个推理、调度、机器人执行链路配合得比较好。
