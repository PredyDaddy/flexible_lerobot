## 1. 一句话总结

`my_devs/vla_engineering` 不是简单把原版 VLASH 放进仓库，而是围绕当前 `flexible_lerobot` 里的 LeRobot PI0.5 checkpoint，做了一套隔离的 VLA 推理工程化实验区。

这里主要完成了三类工作：

1. 保留 `vlash-main` 作为原版 VLASH 参考，用来研究异步 action chunk、future-state-aware、`torch.compile`、LoRA/QLoRA、benchmark 等机制。
2. 新增 `vlash_iner`，把当前仓库训练出来的 PI0.5 checkpoint 接入同步推理、异步 chunk runtime、SO101/SO100 机器人运行时、安全检查、服务化推理和分级验收流程。
3. 在服务化链路上继续接入 `torch`、`torch_compile`、`tensorrt_split` 三种后端，使 TensorRT split engine 可以复用同一套机器人客户端和异步调度逻辑。

整体路线可以概括为：

```text
原版 VLASH 思想
  -> 当前 LeRobot PI0.5 checkpoint
  -> vlash_iner 隔离推理工程
  -> 本地同步 / 本地异步
  -> FastAPI 服务化推理
  -> TensorRT split 后端
  -> SO101 只读和实机验收
```

这条路线的重点是：**不直接替换 `src/lerobot` 的 PI0.5 模型实现，不把 VLASH policy 整体搬进主包，而是在 `my_devs/vla_engineering` 内独立复用 VLASH 的 runtime 思路。**

## 3. 原版 VLASH 提供了什么

`vlash-main` 是参考基线。它本身提供的主要能力包括：

1. VLA 训练和推理入口：

   - `vlash train ...`
   - `vlash run ...`
   - YAML 配置驱动。

2. LeRobot 集成：

   - 使用 LeRobot dataset、robot、policy 配置体系。
   - 支持 PI0.5、PI0 等 VLA policy。

3. 异步 action chunk 运行时：

   - `VLASHAsyncManager` 管理 `current_chunk`、`next_chunk`、`chunk_index`。
   - 在当前 chunk 还剩若干步时启动下一次推理。
   - 减少 chunk 边界等待，让机器人动作更连续。

4. Future-state-aware：

   - 下一段 chunk 推理时，可以用当前 chunk 末尾 action 近似未来状态。
   - 目标是在异步 overlap 时降低状态滞后。

5. Action quantization：

   - `action_quant_ratio` 支持降低实际下发 action 的频率。
   - 可用于减少执行端负担或提升整体执行速度。

6. `torch.compile` 和 warmup 思路：

   - 推理配置中支持 `compile_model`。
   - 部署前做 warmup，避免首帧或前几帧编译尖峰影响控制。

7. 训练侧高效微调：

   - LoRA / QLoRA 相关配置和工具。
   - shared observation training，减少多 delay 训练时重复编码 observation 的开销。

8. Benchmark 工具：

   - 包含 inference latency benchmark，用于评估 compile、policy、dataset 等配置对延迟的影响。

这些能力对当前仓库很有参考价值，但并不适合原封不动替换当前 `src/lerobot/policies/pi05`。原因是当前仓库的 PI0.5 checkpoint、processor、normalization、tokenizer、本地数据集 schema、SO101 上机脚本都已经和现有 LeRobot 实现绑定。如果直接改用 VLASH 的 policy/model class，会引入 checkpoint key、processor、state token 化、normalization 和机器人 schema 的兼容风险。

## 4. 本目录在 VLASH 基础上新增了什么

### 4.1 新增隔离推理工程 `vlash_iner`

原版 VLASH 是一个通用框架，本仓新增的 `vlash_iner` 则是面向当前项目的 PI0.5 上机推理工作区。

新增目标：

```text
my_devs/train/pi/so101/easy_train.sh 训练产物
  -> 当前 LeRobot PI0.5 checkpoint
  -> vlash_iner 加载
  -> SO101/SO100 本地同步推理
  -> VLASH-style 异步 chunk 推理
  -> 服务化远端推理
  -> TensorRT split 后端
```

这个设计的关键点是：

- 训练继续使用当前仓库的 `lerobot-train --policy.type=pi05`。
- 推理继续加载当前 LeRobot PI0.5 checkpoint。
- checkpoint 自带的 `policy_preprocessor.json` 和 `policy_postprocessor.json` 原样复用。
- 不在第一阶段迁移 VLASH 的 PI0.5 model class。
- 所有实验代码放在 `my_devs/vla_engineering/vlash_iner`，避免污染主框架。

### 4.2 新增 checkpoint artifact 校验和本地 tokenizer 检查

`vlash_iner/common.py` 增加了面向当前 SO101 PI0.5 checkpoint 的校验逻辑。

主要能力：

- 检查 checkpoint 必需文件：
  - `config.json`
  - `model.safetensors`
  - `policy_preprocessor.json`
  - `policy_postprocessor.json`
  - normalizer / unnormalizer safetensors
  - `train_config.json`
- 校验输入输出 feature：
  - `observation.images.top`
  - `observation.images.wrist`
  - `observation.state`
  - `action`
- 校验 SO follower 常用维度：
  - state dim = 6
  - action dim = 6
  - image shape = `[3, 480, 640]`
- 检查本地 PI0.5 tokenizer 目录：
  - `google/paligemma-3b-pt-224`

这部分是原版 VLASH 没有按当前项目硬件和 checkpoint 约定做的本地工程化补齐。

### 4.3 新增 PI0.5 policy bundle 加载器

`vlash_iner/policy_loader.py` 把 policy 加载拆成可复用模块。

它负责：

- 定位 policy path。
- 校验 checkpoint artifact。
- 检查本地 tokenizer。
- 通过当前仓库的 `PreTrainedConfig.from_pretrained(...)` 读取配置。
- 通过 `get_policy_class(policy_cfg.type)` 加载当前 LeRobot PI0.5 policy。
- 加载 checkpoint 自带 preprocessor/postprocessor。
- 移动到安全 device。
- 设置 `eval()`。
- 提供 `Pi05PolicyBundle.reset()`，统一重置 policy 和 processor。

这相比原版 VLASH 的区别是：**它明确服务于当前 LeRobot checkpoint，不走 VLASH 自己的 policy factory 和模型实现。**

### 4.4 新增 SO101/SO100 机器人运行时拆分

`vlash_iner/robot_runtime.py` 把真实机器人相关逻辑从脚本里拆出来。

主要能力：

- 定义 `RobotRuntimeConfig`。
- 支持 `so100_follower` 和 `so101_follower`。
- 校验：
  - robot type
  - calibration file
  - calibration joints
  - serial port
  - top/wrist camera device
- 构造 `SOFollowerRobotConfig`。
- 构造 top / wrist 两路 `OpenCVCameraConfig`。
- 复用 LeRobot 默认 robot observation/action processor。
- 构造 dataset features。
- 打印运行摘要。

这部分是面向当前硬件的落地补齐。原版 VLASH 有通用 robot run loop，但没有当前项目里 SO101 端口、相机、标定文件、top/wrist schema 的固定约束。

### 4.5 新增动作安全层

`vlash_iner/safety.py` 新增 `ActionSafetyChecker` 和 `validate_action_chunk(...)`。

安全检查包括：

- action 维度是否匹配。
- action chunk 是否为 `[T, A]`。
- 是否包含 NaN。
- 是否包含 Inf。
- 是否超过绝对值阈值。
- 单步 delta 是否超过阈值。

这是把真实上机风险从脚本逻辑里显式抽出，适合本地同步、异步、服务化客户端和验收脚本共同复用。

### 4.6 新增本地同步推理基线

`vlash_iner/run_pi05_sync.py` 是从当前项目已有 PI0.5 上机脚本整理出来的同步推理入口。

它的作用是建立一个最小可控基线：

```text
robot.get_observation()
  -> robot_observation_processor
  -> build_dataset_frame
  -> predict_action
  -> make_robot_action
  -> safety check
  -> robot_action_processor
  -> robot.send_action
```

支持能力：

- `--dry-run`：只打印配置，不接机器人、不加载模型。
- `--check-policy-load`：只验证 policy 和 processor 加载。
- `--policy-path`：显式指定训练输出 checkpoint。
- `--task` / `--task-id`：支持多任务语言指令。
- robot port、camera、fourcc、fps 等参数化。
- `--max-action-abs` 和 `--max-action-delta` 安全阈值。

这一步的意义是：在做异步和服务化之前，先确认当前 checkpoint 可以按当前仓库的 PI0.5 loader 正常加载和上机。

### 4.7 新增本地异步 action chunk runtime

`vlash_iner/async_manager.py` 是在 VLASH `VLASHAsyncManager` 思想基础上的本地改造版。

它保留的 VLASH 核心思想：

- `current_chunk`
- `next_chunk`
- `chunk_index`
- `n_action_steps`
- `overlap_steps`
- chunk 边界切换
- 提前触发下一次推理
- 可选 future-state-aware

新增或强化的地方：

- 支持 `ThreadPoolExecutor` 后台预取下一段 chunk。
- 支持 `pending_inference`、`wait_count`、`inference_count` 等统计。
- 支持 chunk 切换处的不连续性统计：
  - `last_switch_delta_abs_max`
  - `max_switch_delta_abs_max`
  - `last_switch_delta_l2`
  - `switch_direction_flip_count`
- 支持 `chunk_blend_steps`，在新 chunk 开头用前一个 action 做简单平滑过渡。
- 对 action chunk 做统一 shape 和 NaN/Inf 校验。
- future state 作为可选项，不默认强行开启。

`vlash_iner/run_pi05_async.py` 把这个 manager 接到真实机器人循环。

这相比原版 VLASH 的重要变化是：**异步 manager 被改造成一个与 policy 类型解耦的通用 chunk 调度器，通过 `predict_chunk_fn(observation, future_state)` 接入当前 LeRobot PI0.5。**

### 4.8 对 future-state-aware 和 action quantization 做了保守处理

原版 VLASH 强调 future-state-aware 和 action quantization 的收益。本仓在第一阶段做了更保守的工程选择。

原因是当前 LeRobot PI0.5 的 processor 会把 `observation.state`：

```text
归一化
  -> 离散化
  -> 拼进 language prompt
  -> 进入 tokenizer
```

因此 future-state-aware 不是简单替换一个连续 state tensor，而是会改变 prefix language tokens。它可能有效，但需要单独 A/B 验证。

所以当前策略是：

- `future_state_aware` 支持参数，但验收默认关闭。
- `action_quant_ratio > 1` 在本地异步和远端异步实现里显式禁用。
- 第一阶段保持 `action_quant_ratio = 1`，避免跳步执行语义未验证时直接控制机械臂。

这是一处和原版 VLASH 明显不同的安全取舍。

### 4.9 新增 torch.compile warmup 和可选编译运行

`vlash_iner/run_pi05_compile_warmup.py` 新增了当前 PI0.5 的编译预热入口。

它做的事情：

- 加载当前 LeRobot PI0.5 checkpoint。
- 强制开启 `compile_model=True`。
- 使用 dummy top/wrist image 和 zero state 触发 `predict_action_chunk`。
- 记录 warmup 每步耗时和输出 shape。
- 可选接真实机器人运行异步 loop。

相关技术文档里记录过一组服务化异步优化观察：

```text
torch.compile 冷编译 + warmup 总耗时：约 95.38s
compile 后稳定推理：约 52-68ms / 50-step action chunk
不开 compile 稳定推理：约 97ms / chunk
compile 稳定平均：约 56ms / chunk
```

这说明 `torch.compile + warmup` 在当前部署场景里有明确收益，但也必须接受冷编译耗时，适合服务端常驻模式。

### 4.10 新增服务化推理链路

`vlash_iner/server` 新增了 PI0.5 服务端和机器人客户端。

服务端入口：

```text
vlash_iner.server.run_pi05_async_server
```

客户端入口：

```text
vlash_iner.server.run_pi05_async_client
```

服务端提供：

- `GET /health`
- `POST /reset`
- `POST /infer`

服务端能力：

- 常驻加载 PI0.5 checkpoint。
- 加载 checkpoint 自带 preprocessor/postprocessor。
- 支持 `torch` 后端。
- 支持 `torch_compile` 后端。
- 支持 `tensorrt_split` 后端。
- 接收 observation、task、robot_type、future_state、n_action_steps。
- 返回 action chunk、infer time、backend 信息。

客户端能力：

- 连接真实 SO101/SO100 follower 和相机。
- 构造 LeRobot observation frame。
- 通过 HTTP/pickle 调用服务端。
- 使用 `AsyncChunkManager` 管理远端 action chunk。
- 支持后台请求下一段 chunk。
- 支持只读模式 `--no-send-action true`。
- 真实发送 action 必须显式 `--confirm-control true`。
- 输出 JSON 验收报告。

相比原版 VLASH 本地 `vlash run`，这是一个更贴近部署的分布式结构：

```text
机器人客户端：采集 observation、调度 chunk、做安全检查、发 action
模型服务端：常驻模型、执行 PI0.5 推理、返回 action chunk
```

它也吸收了 Realtime-VLA V2 中服务端/客户端拆分的思路，但保留了当前 LeRobot PI0.5 checkpoint 和 SO101 runtime。

### 4.11 新增 TensorRT split 后端接入

服务端的 `--backend tensorrt_split` 是本目录在 VLASH 基础上最重要的新增部署能力之一。

接入边界：

```text
客户端机器人层不变：
  robot.get_observation
  HTTP /infer
  AsyncChunkManager
  safety check
  robot.send_action

服务端协议层不变：
  observation -> action_chunk

模型后端可替换：
  torch
  torch_compile
  tensorrt_split
```

TensorRT 接入方式：

```text
加载 LeRobot PI0.5 policy
  -> 加载 prefix_cache engine
  -> 加载 denoise_step engine
  -> patch_sample_actions_with_split_trt(policy, ...)
  -> 继续通过 policy.predict_action_chunk(...)
```

当前 engine：

```text
my_devs/openpi_trt/artifacts/pi05_so101_prefix_cache_b1_fp32.engine
my_devs/openpi_trt/artifacts/pi05_so101_denoise_step_b1_fp32.engine
```

当前服务端参数中使用：

```text
--trt-model-dtype float32
```

这比原版 VLASH 多了一层真正的部署后端替换能力：VLASH 主要是 PyTorch 级异步和 compile；这里进一步把服务端模型内部后端替换成已经导出的 split TensorRT engine。

### 4.12 新增分级验收脚本和证据报告

`vlash_iner/server` 增加了分级验收：

- `run_pi05_backend_acceptance.py`
- `run_pi05_acceptance_audit.py`
- `run_pi05_robot_acceptance.py`

验收分层：

```text
L1 infer 100:
  连续 100 次 /infer，验证服务端稳定返回 action chunk。

L1 async mock 120s:
  不接机器人，用 AsyncChunkManager 模拟 45Hz 异步控制 120 秒。

L2 readonly 60s:
  连接真实机器人和相机，采集真实 observation，调用服务端，但不发送 action。

L2 lowspeed robot 20s:
  低速真实发送 action。

L3 main robot 120s:
  主配置真实运行 120 秒。
```

这套验收是原版 VLASH 没有按当前项目做的。它把“模型能跑”和“机器人能安全上机”之间的步骤拆开，避免直接从离线推理跳到真实控制。

## 6. 和原版 VLASH 的差异总结

下面按能力对比说明本目录在原版 VLASH 基础上的新增和调整。

| 维度 | 原版 VLASH | 本目录新增/调整 |
| --- | --- | --- |
| 代码定位 | 通用 VLA 框架 | 当前仓库 PI0.5 上机推理工程区 |
| 模型实现 | 使用 VLASH 自己的 policy/model factory | 保留当前 LeRobot PI0.5 policy，不替换 `src/lerobot` |
| checkpoint | 面向 VLASH 训练/推理配置 | 直接加载 `easy_train.sh` 产出的 LeRobot PI0.5 checkpoint |
| processor | 走 VLASH/LeRobot 通用流程 | 强制复用 checkpoint 自带 preprocessor/postprocessor |
| tokenizer | 通用配置 | 增加本地离线 tokenizer 目录检查 |
| robot | 通用 LeRobot robot run | 固化 SO101/SO100 follower、top/wrist camera、serial port、calibration 校验 |
| 同步推理 | 有通用 run loop | 新增当前项目同步 baseline `run_pi05_sync.py` |
| 异步调度 | `VLASHAsyncManager` | 新增解耦版 `AsyncChunkManager`，支持后台线程、统计、blend、安全校验 |
| future-state-aware | 核心特性之一 | 支持但默认谨慎关闭，避免 PI0.5 prompt state 语义未验证 |
| action quantization | 支持 `action_quant_ratio` | 参数保留，但 `>1` 显式禁用，等待执行语义验证 |
| compile | 支持 `torch.compile` | 新增当前 checkpoint 的 compile warmup 和服务端常驻模式 |
| 服务化 | 原版主要本地运行 | 新增 FastAPI 服务端和机器人客户端 |
| 后端 | 主要 PyTorch/compile | 新增 `torch` / `torch_compile` / `tensorrt_split` 后端切换 |
| TensorRT | 非本目录原版能力 | 接入 split TensorRT prefix_cache / denoise_step engine |
| 验收 | benchmark 和运行示例 | 新增 L1/L2/L3 分级验收、JSON report、audit gate |
| 安全 | 通用控制流程 | 新增动作维度、NaN/Inf、abs、delta、confirm-control、no-send-action 等安全门 |

一句话概括：

```text
原版 VLASH 提供了“异步 VLA 推理怎么做”的框架思想；
本目录把这个思想改造成“当前 LeRobot PI0.5 + SO101 + 服务化 + TensorRT + 分级验收”的本地部署工程。
```

## 7. 为什么没有直接搬 VLASH 模型

当前工作刻意没有把 `vlash-main/vlash/policies/pi05/modeling_pi05.py` 直接替换到 `src/lerobot`，原因包括：

1. 当前训练产物来自本仓 `lerobot-train --policy.type=pi05`，checkpoint 和当前 LeRobot PI0.5 loader 天然匹配。
2. PI0.5 的 processor 会把 state 离散后拼进语言 prompt，processor 差异会直接影响 prefix tokens。
3. checkpoint 自带 normalizer/unnormalizer 是部署真相，不应由 VLASH 默认配置替代。
4. 直接迁移 VLASH policy/model 会引入 key remapping、state conditioning、fusion、LoRA/QLoRA、compile 图结构等多重兼容风险。
5. 当前目标是先让机器人推理链路稳定跑通，再逐步替换后端或优化 runtime。

所以本目录采用的是低风险路径：

```text
模型和 checkpoint 仍用当前 LeRobot PI0.5；
runtime 思路借鉴 VLASH；
性能后端通过服务端 patch 接入 TensorRT；
所有风险隔离在 my_devs/vla_engineering。
```

## 9. 当前风险和注意事项

### 9.1 future-state-aware 仍需单独验证

当前 PI0.5 state 会进入 language prompt。直接用 future action 替换 state，可能改变 token 分布。建议先保持：

```text
--future-state-aware false
```

等同步/异步 baseline 稳定后，再做 A/B 测试。

### 9.2 action_quant_ratio 尚未完成执行语义验证

当前代码显式禁止：

```text
action_quant_ratio > 1
```

这是合理的。跳步发送 action 可能影响接触任务精度，也可能改变低层控制器收到的轨迹密度。后续要结合轨迹平滑、速度限制和任务成功率验证。

### 9.3 TensorRT 当前是 FP32 split engine

当前接入的是：

```text
prefix_cache FP32 engine
denoise_step FP32 engine
```

服务端也按：

```text
--trt-model-dtype float32
```

加载。后续如果切 FP16/BF16 engine，需要重新做 Torch/ONNX/TRT 一致性、服务端 L1/L2/L3 验收。

### 9.4 L3 主跑证据不能混用 torch 和 TRT

已有 `trt_main_robot_120s.json` 中 backend 是 `torch` 且运行中断，不能作为 `tensorrt_split` 主跑通过依据。

后续应重新生成：

```text
trt_lowspeed_robot_20s.json
trt_main_robot_120s.json
```

并确认：

```text
health.backend == tensorrt_split
finished == true
error == null
wait_count == 0
```

### 9.5 服务协议当前仍是 HTTP + pickle

这对本地实验足够方便，但长期部署要注意：

- pickle 不适合作为不可信网络协议。
- 跨语言兼容性弱。
- request/response schema 没有强类型约束。

后续可以考虑 JSON metadata + binary image、msgpack、gRPC 或共享内存方案。

## 10. 建议的后续收口

建议按下面顺序推进：

1. 补齐 L2 低速真机 20 秒：

   ```text
   backend = tensorrt_split
   confirm_control = true
   no_send_action = false
   run_time_s = 20
   overlap = 0
   background_inference = false
   ```

2. L2 通过后再跑 L3 主配置 120 秒：

   ```text
   backend = tensorrt_split
   control_fps = 45
   inference_overlap_steps = 8
   background_inference = true
   chunk_blend_steps = 2
   future_state_aware = false
   action_quant_ratio = 1
   ```

3. 用 `run_pi05_acceptance_audit.py --strict` 重新生成严格审计报告。

4. 若 L3 稳定，再比较三种后端：

   - `torch`
   - `torch_compile`
   - `tensorrt_split`

   指标包括：

   - request latency p50/p95
   - server infer p50/p95
   - wait_count
   - observed_hz
   - chunk 切换 delta
   - 真实任务成功率
   - 机器人动作平滑性

5. 最后再打开更激进能力：

   - future-state-aware A/B
   - action quantization
   - FP16/BF16 TensorRT engine
   - 更明确的服务协议
   - 时间轴平滑或 MPC

## 11. 最终结论

`my_devs/vla_engineering` 当前完成的是一套从 VLASH 思想到本仓 PI0.5 实际上机部署的工程化落地。

它相对原版 VLASH 的核心新增不是某一个单点优化，而是一整条本地部署链路：

```text
当前 LeRobot PI0.5 checkpoint 加载

  + action safety

```

当前可确认的工程状态是：

```text

可以进入低速真实发送动作验收；
完整实机动作闭环尚未最终收口。
```

因此，这个目录已经从“参考 VLASH”推进到了“可用于当前 PI0.5/SO101 部署验收的工程工作区”，下一步重点应放在补齐 `tensorrt_split` 的 L2 lowspeed 和 L3 main 实机证据。
