## 1. 第一阶段结论

第一阶段已经打通并验证了以下链路：

```text
VR 输入
  -> X86 Pink/Pinocchio IK + Meshcat
  -> target_action UDP 39030
  -> LeRobot recorder
  -> JZRobotPinTimed
  -> command UDP 39020
  -> Orin Phase 3 executor

Orin 四路 ROS state source
  -> 30 Hz state snapshot + source_timing v1
  -> state UDP 39010
  -> JZRobotPinTimed

Orin 三路 RTSP
  -> X86 PyAV timed receiver
  -> 选择与 state 接收时刻最近的缓存帧
  -> Parquet + H.264 MP4 + timing JSONL

正式三条数据
  -> 数据/视频/动作跟随检查
  -> source/camera/action/command 时序检查
  -> ACT 20 epoch 训练
  -> checkpoint 离线加载与 18D 推理
```

已经有一份正式 armed 数据通过全部当前检查：

```text
tests/outputs/jz_robot_pin_timed_real_20260711_190502
```

也已经实际完成一次 20 epoch ACT 训练：

```text
tests/outputs/act_jz_robot_pin_timed_real_20260711_190502_e20_b16_r224
```

但这不表示系统已经可以直接进入规模化训练或 armed 推理。当前只有 3 个 episode，action 与反馈

## 4. 18 维数据契约

最初讨论中曾把维度误认为 14；后续已确认正式 schema 是 18 维：

```text
left joints:   7
right joints:  7
left gripper:  width + force
right gripper: width + force
total:         18
```

`action` 与 `observation.state` 的字段名和顺序必须一致：

```text
left_left_joint1.pos ... left_left_joint7.pos
right_right_joint1.pos ... right_right_joint7.pos
left_gripper.width
left_gripper.force
right_gripper.width
right_gripper.force
```

时序诊断信息没有塞入 observation，因此不会改变训练输入 schema。它单独保存到：

```text
<dataset_root>/meta/timing/episode-XXXXXX.jsonl
```

## 5. 从原 Pin 到 Timed Pin 的演进

### 5.1 原 `jz_robot_pin` 阶段

原 Pin 在 `jz_robot_udp` 之上增加了：

- 18D 双臂/双夹爪 Robot；
- UDP state 与 command；
- target-action teleoperator；
- 三路 RTSP；
- record/replay/teleop 脚本；
- initial delta、step delta、armed 环境门；
- 三条 episode 的数据检查。

这一阶段解决了“能遥操、能控制、能录三路视频和 18D 数据”的问题，但不能可靠回答：某个
dataset frame 对应的是哪个 state packet、哪个 decoder frame、哪个 target-action packet，以及
最终 command 在本机何时发送完成。

### 5.2 新建 `jz_robot_pin_timed` 的原因

没有时序证据时，视频看起来掉帧或 action/state 不一致只能靠猜。为了不破坏旧 Robot，新增：

```text
JZRobotUDP -> JZRobotPin -> JZRobotPinTimed
```

Timed 子类复用原协议、18D 字段、安全处理与 command 发送，仅增加：

- PyAV RTSP 缓存、decoder PTS、decoder sequence 和本机 decoder-output 时间；
- 按 state 本机接收时刻选择最近相机帧；
- observation/action/command hook；
- 每个保存帧一条 timing sidecar；
- 严格的 source、camera、action、command 检查。

旧 `jz_robot_pin` 仍可回退使用，不需要同时重写 Orin command 协议。


### 6.2 第一帧和连续步长门禁反复阻塞现场录制

早期风险是默认值 `0.0` 等效于关闭第一帧保护；修复后核心 Robot 与通用 record/replay 默认改为
`0.02 rad` 且 armed 模式 fail-closed。现场实际控制和遥操作跟随误差较大，随后出现：

- initial delta 超过 `0.02`；
- 放到 `0.15` 后仍可能超过；
- step delta 仅比 `0.02` 多约 `1.3e-5 rad` 也会终止；
- 某些起始姿态差达到 `0.33 rad`。

用户明确选择优先推进现场开发，并安排人员守急停，因此“三条现场录制包装器”将 initial 和 step
阈值设为 `10.0 rad`，对正常机械臂关节范围等效于放开。

必须区分：

- `JZRobotPin`、`JZRobotPinTimed`、通用 `record.sh`、`replay.sh` 默认仍是 `0.02 rad`；
- 只有 `data_check/record_and_check_3.sh` 的现场三条包装器默认使用 `10.0 rad`；
- 这不是安全结论，而是已知现场取舍；不能把 10 rad 扩散成全局默认；
- replay 仍应先让机器人姿态靠近 episode 第一帧，再保留保守阈值。

还必须注意当前 Orin armed executor 配置
`udp_test/test_scripts/arm_side/orin_phase3_executor_config_armed_hold.yaml` 显式设置：

```yaml
allow_publish_rate_limit_bypass: true
allow_joint_position_limit_bypass: true
allow_joint_delta_limit_bypass: true
allow_gripper_limit_bypass: true
allow_gripper_delta_limit_bypass: true
```

因此正式三条 armed 采集时，X86 的数值变化门和 Orin 的多项 position/delta/gripper limit 都被大幅
放开。仍然保留 armed 确认、sender IP、packet freshness、schema、sequence 和 timeout 等门禁，但
物理急停和现场人员承担了主要运动风险。下一阶段不能把这一状态描述成完整的软件安全闭环。

### 6.3 target action 首包超时与 stale 语义

录制曾报：

```text
Timed out waiting for the first JZRobot UDP target action packet on 0.0.0.0:39030
```

根因通常不是 recorder 本身，而是 joystick publisher 未启动、已退出、发往错误端口，或本机端口
被其他 probe/control 占用。

处理：

- joystick 使用 `publish_mode=always`，持续发布当前保持目标；
- recorder 等待首包默认 5 秒；
- 包增加 stamp age、future skew、seq 顺序和 seq reset 检查；
- 通用 teleop 仍支持 observation-aware `hold_current`；
- 正式录制默认 `stale_policy=raise`，输入失联时立即失败，不把 hold-current 静默写进数据；调用者
  技术上仍可用环境变量覆盖，但后置 timing checker 默认会拒绝 `hold_current` 来源；
- timing checker 默认不允许 action source 为 `hold_current`。

这解决了“看似持续有新命令、实际输入源已经失联”的掩盖问题。

### 6.4 recorder、teleop 和控制权关系

早期操作说明把遥操和录制拆开，造成误解。正确所有权是：

- joystick 只做 VR、IK、Meshcat 和 target action 发布；
- recorder 自己读取 state、读取 target action、发送 command 并保存数据；
- 录制时不能再启动 `start_teleop.sh` 或 `start_pin_control.sh`，否则两个进程争用 state/command；
- probe、recorder 和 control 都绑定 X86 `39010`，三者不能同时运行。

reset 阶段的设计是：recorder 继续跑遥操控制循环并发送动作，但不保存 dataset frame。因此操作者在
两条 episode 之间按回位键，回位动作一般不会进入数据集；如果在 episode 的有效录制时间内按回位，
则会被录入。日志会明确打印：

```text
Reset control active for 5.000s: teleop commands continue; dataset frames are not saved
```

### 6.5 Start Recording 语音与 SSH headless 警告

用户要求每条真正开始保存时播放语音，并在终端有对应日志。`lerobot_record` 改为在第一帧实际进入
dataset 时打印并调用 `log_say("Start recording episode ...")`，而不是仅在准备阶段播报。

SSH 终端没有 X server 时，`pynput` 会报 `Bad display name ""` 并进入 headless。这意味着：

- recorder 窗口不显示相机；
- recorder 不能用本地键盘控制流程；
- 不妨碍自动三条录制、RTSP 解码和数据保存；
- 遥操可视化由独立 Meshcat 浏览器提供。

该警告不是前述录制失败的根因。

### 6.6 数据保存必须使用实际发送动作

原始 recorder 可能保存进入 `send_action()` 前的 action，不能反映 float 转换、夹爪限幅和安全处理。
现已改为保存 `Robot.send_action()` 返回的实际发送 action，Rerun 与 dataset 使用同一份值。

Parquet 中的 `action` 因而是安全处理后实际交给底层发送的 18D command，而不是原始遥操输入。
Timing sidecar 不保存 18 个数值本身，只保存 matching command 的 seq/stamp、mode、transport、
send-completed 时间和 `action_key_count=18`。当前 checker 能证明同一 observation 发生过一个 18-key
command，但不能仅凭 sidecar 逐值证明它等于 Parquet action。

### 6.7 视频模糊、亮色异常与 CRF

旧正式编码使用 H.264 CRF 30。CRF 越低，编码保真度通常越高、码率和文件越大。现场对 CRF
18/20/22/30 做视觉对照后，用户确认 CRF 18 最符合需求，因此 timed 正式流程固定：

```text
codec=h264
crf=18
pix_fmt=yuv420p
gop=2
fps=30
```

历史右腕对照报告中，CRF 18 约为 3.60 Mbps、SSIM 0.9818、PSNR 44.59 dB；CRF 30 约为
0.75 Mbps、SSIM 0.9613、PSNR 39.69 dB。该结果支持“CRF 18 的二次编码损失更小”，但它是
对当次样本的对照，不是所有场景下固定码率或视觉质量的保证。

CRF 18 只减少 X86 把已解码帧重新编码为训练视频时的损失。它不能修复：

- 相机曝光、白平衡、ISP 本身的问题；
- Orin camera bridge 输出前已经产生的压缩或颜色错误；
- RTSP 网络丢包；
- YUV/RGB range 或 BT.709 metadata 错误。

Orin 侧 Agent 曾为外部 `teleop_ws/camera_bridge` 准备颜色 metadata patch，并报告 SHA256：

```text
acc0ff03f64d7fdd5cfead38bd468dce254ccb5caa365e8db9925ca3eeeabc29
```

该 camera bridge 目录不在本仓库 Git 中，patch 也不在当前 X86 工作树内。历史报告明确说当时没有
重启现场 camera bridge。因此新 Agent 必须把它视为外部部署项，不能仅凭本仓库 commit 假定颜色
修复已经在实时流中生效。

### 6.8 Meshcat 慢、只显示双臂或页面空白

用户要求整机显示并达到 30 Hz。当前共享 joystick 默认：

```text
VISUAL_FREQUENCY=90
DISPLAY_EVERY=3
VISUALIZE_WHOLE_ROBOT=true
```

即 IK/target action 约 90 Hz，Meshcat 目标 30 Hz，并传 `--no-arm-meshes-only` 加载整机 visual
meshes。日志会打印目标和实测 `meshcat_hz`、平均/最大 display 时间与 loop overrun。

现场曾出现 `http://10.1.42.3:7000/static/` 空白，重启 joystick 后恢复。当前结论是存在启动/浏览器
连接的间歇问题，但没有稳定复现和根因证明。新 Agent 不应把“重启后恢复”写成已根治；需要保留
启动日志、确认 7000 端口和 Meshcat URL、检查 `visual meshes loaded`。

另一个部署风险是 `my_devs/my_var_tp` 仍被根 `.gitignore` 忽略。当前机器有完整目录，所以能运行；
干净 clone 不具备可复现的 VR/IK/Meshcat 发布端。这是第一阶段明确延期项。

### 6.9 第一版 timed 录制在视频编码后段错误

第一版 timed 三条已经采完并编码完三路视频，但 Python 在退出时出现 segmentation fault。症状位于
录制资源清理阶段，不是 action/state 采集阶段。后续 capture hardening 将 timed PyAV reader 改为
非 daemon 线程、有序 stop/join 和更严格的容器生命周期，并加强 source/timing 检查。

后续 `190502` 正式三条能完整结束并自动生成两份 PASS 报告，说明当前路径没有复现该段错误。
但没有 core backtrace 能单独证明最初 segfault 的唯一根因，所以文档结论应是“当前实现和正式样本
不再复现”，不是“根因已被百分之百证明”。

### 6.10 Orin 标称 30 Hz、实际只有约 6～10 Hz

Timed 最初把 state bridge 配成 30 Hz，但启动日志测得只有约 8.9 Hz，大量 skip 原因为：

```text
stale
skew
not_advanced
```

ROS CLI 只读测量证明源 topic 本身足够快：

- 左右双臂约 200 Hz；
- 左右夹爪约 100 Hz；
- 没有观察到 50/100 ms 级 publisher 停顿。

真正根因是同一 Python 进程内 rclpy executor/GIL 调度会间歇饿死某一路 callback，现场最明显的是
left gripper。先尝试 MultiThreadedExecutor + ReentrantCallbackGroup 仍不稳定，最终改为四个独立
spawned 进程：

```text
left_joints worker
right_joints worker
left_gripper worker
right_gripper worker
```

每个 worker 独享 ROS Context、Node、MutuallyExclusiveCallbackGroup 和 SingleThreadedExecutor，
通过 Pipe 把最新 source 传回主进程，由非 daemon IPC collector 原子更新 snapshot；退出时使用
Event、join，必要时 terminate/kill 完整回收。

最终三轮 dry-run 现场报告：

| 轮次 | state Hz | 最大 source age | 最大 source skew | payload | 窗口 skip 增量 |
|---:|---:|---:|---:|---:|---:|
| 1 | 30.000031 | 11.829 ms | 10.564 ms | 1373 B | 0 |
| 2 | 30.028202 | 11.509 ms | 10.096 ms | 1374 B | 0 |
| 3 | 30.003028 | 8.260 ms | 7.661 ms | 1372 B | 0 |

三轮都出现 `replay services ready`，executor 明确为 dry-run 且不发布 ROS command topic，停止后无
bridge/receiver/executor 残留。

### 6.11 `conda run` PID 识别失败

Orin 启动链最初把 `conda run ... python` 的 conda wrapper 当成 bridge Python 进程。bridge 日志
打印真实 child PID，而 readiness 等待 wrapper PID，二者永远不一致，最终误报 hz verification
失败。

修复：

- 只把 argv 形如 `python <orin_ros_state_udp_bridge.py> ...` 的进程视为真实 bridge；
- 先搜索 launcher descendants，最后才检查 launcher；
- `STATE_PROCESS_START_TIMEOUT_S` 默认/透传为 30 秒；
- readiness 同时校验 `/proc/<pid>/cmdline`、startup metadata、日志 PID 和配置 Hz。

### 6.12 source timing 与 30 Hz readiness

`source_timing v1` 是 state packet version 1 的可选扩展，旧消费者仍可解析；正式 timed 三条再强制
每帧必须存在。默认 Orin 合约：

```text
STATE_HZ=30
MAX_SOURCE_AGE_MS=50
MAX_SOURCE_SKEW_MS=20
REQUIRE_ALL_SOURCES_ADVANCED=true
MIN_MEASURED_STATE_HZ_RATIO=0.9
```

因此 `replay services ready` 不再只表示命令行写了 `--hz 30`，还要求启动 executor 前后两个实测
窗口达到至少 27 Hz。

典型 packet 约 1372～1374 bytes，低于常见 Ethernet/IPv4 1472-byte UDP payload，但余量很小；
若部署路径 MTU 小于 1500，仍需观察 `bytes=` 并评估分片风险。

### 6.13 action/state lag 检查阈值

旧检查要求 `action_t == observation.state_(t+1)` 不符合实际控制器延迟。检查改为在未来多帧中搜索
best lag，并对 moving joint frames 计算 MAE/P95。

一次样本因 P95 `0.030183 rad` 比旧阈值 `0.030000 rad` 高 `0.000183 rad` 被判 FAIL。用户确认该
运控误差可以接受，因此 timed 三条包装器把 P95 默认阈值改为可配置 `0.05 rad`；MAE 0.01、18D、
视频和 source timing 检查没有放宽。

正式 `data_check_report.json` 只保存 lag 1～6。本文生成时另做了一次只读扩展检查，把最终

## 7. Timed 实现的核心语义

### 7.1 X86 timing sidecar

每个 dataset frame 对应一条 JSONL，主要字段：

```text
session_id
episode_index, frame_index, observation_sequence
state.packet_seq/stamp/receive_wall/receive_monotonic/source_timing
cameras.<name>.decoder_pts/receive times/sequence/generation/age/reused/skew
action.source/packet_seq/stamp/receive times/age
command.observation_sequence/seq/stamp/mode/transport/send-completed/action-key-count
```

约束：

- sidecar 与 Parquet 的 `(episode_index, frame_index)` 一一对应；
- 同一 `session_id` 内 observation sequence 严格递增；
- resume 新进程使用新 session；
- command 必须关联同一个 observation；
- command metadata 必须表明本轮发送了 18 个 action key；具体 18D 数值存于 Parquet `action`，
  sidecar 不保存 action vector，也不做逐值副本校验；
- episode 从 frame 0 重录时覆盖旧 sidecar；
- codec/CRF 写入 `meta/info.json.video_encoding`，resume 时必须一致。

### 7.2 Orin `source_timing v1`

四个 source：

```text
left_joints
right_joints
left_gripper
right_gripper
```

每个 source 包含 generation、callback 接收 wall/monotonic、可选 ROS header stamp 和 age。双臂保留
ROS header stamp；夹爪消息没有 header，所以为 `null`。`source_skew_ms` 是四路 callback 接收
monotonic 的最大值减最小值。

协议 schema：

```text
my_devs/jz_robot_pin_timed/schema/source_timing_v1.schema.json
my_devs/jz_robot_pin_timed/schema/source_timing_v1.example.json
```

### 7.3 时间戳不能证明什么

当前实现解决的是“本机可观测和可核对”，不是硬件同步：

- camera `receive_*` 是 decoder 交出 frame 后、像素转换前的时间，不是网络包到达或曝光时间；
- decoder PTS 是流内相对时间，不保证三路共用硬件时钟；
- Orin packet stamp 与 X86 clock 未经 PTP/chrony 校准，不能直接跨机相减；
- command send-completed 表示 X86 `send()` 返回，不是 Orin 收包、ROS publish 或电机执行确认；
- 夹爪 age 是 ROS callback 新鲜度，不是夹爪硬件采样年龄。

若下一阶段要证明传感器/执行器端到端同步，需要 PTP/chrony、源曝光/采样时间戳和 executor ack。

## 10. ACT 20 Epoch 训练

### 10.1 为什么需要 resize wrapper

三路原图 shape 不一致：

```text
head:  720x1280
left:  480x640
right: 480x640
```

ACT 多相机输入要求送入模型的图像 shape 一致，且原分辨率会产生过多 ResNet/Transformer token。
训练入口在标准 preprocessor 中插入 `ImageCropResizeProcessorStep(224,224)`，并把它序列化进
checkpoint，保证训练和后续推理使用同一个 resize。

注意：`train_config.json` 仍保存数据集原始 image feature shape，这是预期行为；实际送入模型前，
`policy_preprocessor.json` 中的 resize step 会把三路变成 `(3,224,224)`。

6. 研究约 7 帧经验最佳对齐的成因与标签方案；先离线比较原标签、lag-shift 标签与模型误差，
   不预设它全部来自网络或控制器延迟。
7. 为 checkpoint 增加纯离线批量评估和 action range/速度检查。
8. 获得用户许可后先做 local/dry-run policy 推理；审阅输出后再讨论 armed。

### 13.3 禁止直接做的事情

- 不得因“之前上过机”而默认拥有本轮机器人控制权限；
- 不得同时启动 probe、recorder 和 control；
- 不得在 recorder 运行时另开 teleop control；
- 不得把三条包装器的 10 rad 复制成 Robot/replay 全局默认；
- 不得把 decoder output time 描述成曝光时间；
- 不得把训练 loss 下降描述成实机策略已经可用；
- 不得覆盖或删除用户未跟踪文件；
- 不得为了方便把 `4036f64` 再 merge 到当前集成分支。

### 13.4 2026-07-12 直连 RealSense ZMQ 路径

Orin commit `3e5ae1a23e7b7a52831397e88f65ff0df9471d85` 增加三路 RealSense RGB8 -> JPEG/ZMQ
publisher，绕过 robot_camera、SHM、camera_bridge、NV12、H.264、RTSP 和 PyAV。X86 timed robot
对应增加严格 `jz_realsense_zmq/v1` receiver：每路独立 SUB + CONFLATE，校验相机名、sequence、
尺寸、RGB8/JPEG 和 payload，`cv2.imdecode` 后显式 BGR -> RGB。

sidecar 的 ZMQ camera schema 保存 Orin `camera_timing` 原对象、X86 receive/decode 时间、sequence gap、
frame age 和 state receive skew。Orin monotonic 只用于 Orin 内部 capture/encode 间隔；X86 monotonic
只用于 X86 receive/decode/state 间隔，两台机器的 monotonic 不相减。旧 RTSP sidecar 保持可读。

现场只读 probe 在 JPEG quality 95、100 Mb/s 链路下得到 head 约 10 FPS、left 27.6 FPS、right
26.3 FPS。三路 JPEG payload 经 JSON base64 后估算约 164 Mb/s，因此当前参数不能进入正式采集。
必须先升级千兆链路、降低 JPEG quality，或改为无 base64 膨胀的二进制 multipart；三路 probe 均
达到至少 25 FPS 且协议错误/乱序为 0 后，才运行完整 recorder dry-run。

## 15. 最终交接判断

第一阶段已经从“能动、能录”推进到“能证明每个保存帧来自哪一组本机可观测输入，并能通过统一
检查后进入 ACT 训练”。当前最有价值的成果不是某个单独阈值，而是：

1. 18D 训练 schema 保持稳定；
2. source/camera/action/command 的时序证据独立保存，不污染训练字段；
3. Orin state bridge 实际稳定达到 30 Hz，而非只在配置上写 30；
4. 正式数据和训练产物都有可复核报告；
5. 安全取舍、时间戳边界和未完成事项被显式记录。

下一阶段的重点应是可复现部署、扩大高质量数据、处理固定控制延迟、建立独立验证集和完成 policy
dry-run，而不是继续通过放宽检查阈值掩盖问题。
