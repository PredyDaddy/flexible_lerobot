# 暂定通信结论

本文档用于和团队同步当前 UDP 通信方案的背景、结构、已完成测试和后续集成建议。

当前阶段只验证通信链路，不接 ROS 控制 topic，不操控机器人。

## 背景

当前机器人主控是 NVIDIA Orin AGX。Orin 上已经运行 ROS2，并能看到机器人相关 topic，例如机械臂、夹爪、AGV、VR、遥操作等。

现在的问题是：

```text
Orin 同时负责 ROS 通信、机器人 I/O、数据处理、lerobot 运行等任务。
当 lerobot 或模型相关逻辑占用大量 CPU/GPU/内存时，Orin 偶尔会处理不过来。
```

目标是把 Orin 从“主计算节点”调整为“机器人通信网关”：

```text
Orin:
  保留 ROS2
  保留机器人硬件接入
  保留安全兜底
  运行轻量 UDP bridge

x86:
  不强依赖 ROS2
  运行 lerobot
  运行后续模型推理、数据处理、录制、调试工具
```

这样可以避免 x86 Ubuntu 24.04 上 ROS 版本不一致的问题，同时通过固定 IP + UDP 做更可控的跨机器通信。

## 已完成测试 1：UDP ping/pong

测试路径：

```text
x86  -> Orin: UDP ping
Orin -> x86:  UDP pong
```

测试命令摘要：

```text
Orin:
  orin_udp_ping_server.py --bind-ip 192.168.1.81 --port 39001

x86:
  x86_udp_ping_client.py --orin-ip 192.168.1.81 --port 39001 --count 20
```

x86 结果：

```text
sent=20
received=20
lost=0
avg_rtt_ms=1.545
max_rtt_ms=1.937
```

结论：

```text
UDP 双向通信正常
20 次请求全部收到回复
丢包 0
往返延迟约 1.5 ms
```

## 注意事项

### age_ms 当前不作为结论依据

x86 日志中出现过：

```text
age_ms=-36158xx.xxx
```

原因：

```text
当前脚本使用 time.monotonic_ns()
monotonic 时间只能在同一台机器内部比较
不能直接跨 Orin 和 x86 计算单向延迟
```

当前可信延迟指标是 ping/pong 的：

```text
rtt_ms
```

如果后续要做单向延迟统计，需要：

```text
方案 A: 两台机器做时间同步
方案 B: 用 ping/pong 估算链路延迟
方案 C: 只统计接收端包间隔和 seq 连续性
```

### hz 统计可以继续优化

当前 6000 包长测结果：

```text
target_hz=20
measured_hz=19.14
```

这个结果可以接受。后续可以优化 receiver 统计方式：

```text
收到第一个包后再开始计时
或者用最近 N 个包做滑动窗口频率统计
```

## 关于 lerobot 机器人注册方式的建议

当前仓库已有：

```text
src/lerobot/robots/jz_robot
```

现有 `jz_robot` 的定位：

```text
ROS2 直连机器人
依赖 rclpy / sensor_msgs / std_msgs
适合运行在 Orin 或完整 ROS2 环境中
直接 subscribe ROS state topic
直接 publish ROS command topic
```

这和当前 UDP 外置计算方案不是同一类接入方式。

### 不建议直接把 UDP 逻辑硬塞进现有 jz_robot

原因：

```text
jz_robot 当前职责是 ROS2 direct robot
UDP 方案的职责是 remote robot client
x86 侧目标是不依赖 ROS2
把两者混在一起会让配置、依赖、安全边界变复杂
```

### 建议新增一个独立 robot type

更推荐：

```text
src/lerobot/robots/jz_robot_udp
```

或者如果希望名字更中性：

```text
src/lerobot/robots/jz_robot_remote
```

不太建议命名为：

```text
jz_robot_web
```

除非后续通信真的会走 HTTP/WebSocket/Web UI。当前方案核心是 UDP，所以 `udp` 或 `remote` 更准确。

推荐命名：

```text
jz_robot_udp
```

它在 lerobot 里的定位应该是：

```text
x86 侧 Robot 实现
不 import rclpy
不直接访问 ROS topic
通过 UDP client 获取 observation
后续通过 UDP client 发送 action
```

## start.sh / stop.sh 的建议

可以有 start/stop 脚本，但它们不应该替代 lerobot 的 Robot 类。

建议职责如下：

```text
arm_start.sh:
  在 Orin 上启动 ROS -> UDP bridge
  绑定 192.168.1.81
  只读阶段只 subscribe ROS topic
  后续控制阶段才允许启动 command receiver

arm_stop.sh:
  停止 Orin bridge 进程
  后续控制阶段需要触发安全停止或进入 read-only

x86_start.sh:
  在 x86 上启动 UDP receiver / lerobot client / 调试日志

x86_stop.sh:
  停止 x86 侧进程
```

但真正给 lerobot 用的机器人接口仍然应该是：

```text
JZRobotUDP.connect()
JZRobotUDP.get_observation()
JZRobotUDP.send_action()
JZRobotUDP.disconnect()
```

这样 lerobot 的 `record`、`teleoperate`、`replay`、后续 policy 推理才能按标准 Robot 接口使用。
