# Phase 3 技术文档：UDP Command 到 Orin ROS Command Publisher

本文档用于约束 Phase 3 的设计、实现边界和验收方式。Phase 3 的目标是让 x86 上的
`JZRobotUDP.send_action()` 可以通过 UDP command packet 控制 Orin 侧 ROS command topic，
但真实 publish 必须被显式 safety gate 保护；默认仍然是 `dry_run`，不能默认让机器人运动。

本文档只写技术约束和实现依据，后续 Agent 应基于本文档再写 `udp_test/docs/phase3/plan.md`。

## 1. 背景

Phase 1 已完成 observation-only 链路：

```text
Orin ROS state topic
  -> UDP state packet
  -> x86 UDP state receiver
  -> x86 RTSP cameras
  -> JZRobotUDP.get_observation()
```

Phase 1 实测结论：

```text
OBS_COUNT=600 PASS
keys=21
numeric=18
三路图像 shape 正常
```

Phase 2 已完成 command dry-run 链路：

```text
x86 JZRobotUDP.action_features
x86 JZRobotUDP.send_action dry-run
UDP command packet v1
x86 -> Orin command dry-run receiver
lerobot-record dry-run
```

Phase 2 实测结论：

```text
x86 -> Orin command dry-run PASS
lerobot-record dry-run PASS
10s * 5fps = 50 command
Orin receiver 收到 idx=50 seq=50
```

Phase 2 的边界非常重要：

```text
不 publish ROS command topic
不控制机器人
Orin command receiver 只校验、打印、统计 command packet
```

Phase 3 要做的事情是补上最后一段：

```text
UDP command packet
  -> Orin executor
  -> safety gate
  -> ROS command publishers
  -> existing robot control chain
```

也就是说，Phase 3 不是重写机器人控制栈，而是在 Orin 上新增一个受门禁保护的 UDP command
executor，把 Phase 2 已验证的 command packet 转换成已有机器人控制链可消费的 ROS message。

### 2.3 推断和待确认点

以下内容是基于 probe 和已有代码的工程推断，不是 probe 直接证明的事实：

```text
1. JointState.position 是 Phase 3 第一版应发布的主要控制字段。
2. JointState.velocity 虽然在 echo sample 中可见 7 值，但 Phase 3 第一版不应填 velocity，
   除非后续明确 velocity 语义、单位、限制和下游控制器需求。
3. Float64MultiArray.data 的顺序应沿用已有 JZRobot 代码：[width, force]。
4. gripper_status sample [100.0, 6.0] 可用于理解状态字段，但不能直接等同于 command limit。
5. 右臂 topic 未抓到持续 hz 样本不代表 topic 不可用；它仍有 publisher count 1 和
   subscription count 1，且 schema 与已有代码一致。正式 armed 测试前仍应做 dry-run topic
   配置检查。
```

## 3. Phase 3 范围

Phase 3 第一版只做：

```text
1. 双臂 JointState command publish
2. 左右夹爪 Float64MultiArray command publish
3. Orin UDP command executor
4. dry_run / armed 两种执行模式
5. explicit armed/active safety gate
6. 各类 command 校验、限幅、限速、超时和 stop 行为
7. Phase 2 dry-run regression 保持通过
```

Phase 3 第一版不做：

```text
1. 底盘 cmd_vel publish
2. policy inference 直接高速控制
3. 默认真实执行
4. 无门禁 publish
5. 绕过 joint / gripper 限制
6. 大规模录制
7. 训练数据质量判断
```

`lerobot-record` 在 Phase 3 可以用于短时 active episode 验证，但第一版不能把 policy inference
作为高速闭环控制入口。先完成低频、小幅度、可人工确认的 command 执行链路，再讨论 policy。

## 4. 架构

目标架构：

```text
x86
  JZRobotUDP.send_action(action)
    -> validate action_features
    -> build UDP command packet v1
    -> send UDP to Orin command port

network
  UDP command packet

Orin
  phase3 UDP command executor
    -> decode command packet
    -> validate sender/schema/mode/seq/stamp/actions
    -> safety gate
    -> dry_run: log only
    -> armed: publish ROS command topics

ROS2 existing robot control chain
  /robot1/telecon/arm_left/joint_commands_input
  /robot1/telecon/arm_right/joint_commands_input
  /robot1/left_gripper/gripper_commands
  /robot1/right_gripper/gripper_commands
```

Phase 3 executor 是 Orin 上的新执行进程，不应把
`udp_test/test_scripts/arm_side/orin_udp_command_receiver.py` 直接无门禁改成默认执行器。
Phase 2 receiver 的价值是协议解析、sender IP、seq 和日志回归参考；Phase 3 必须新增或扩展出
默认 `dry_run`、显式 `armed`、带 safety gates 的 executor 行为。

## 5. 执行模式

Phase 3 至少定义两种模式。

### 5.1 dry_run

默认模式。行为：

```text
1. 绑定 UDP command port
2. 接收 command packet
3. 校验 sender/schema/seq/stamp/actions
4. 运行全部 safety checks
5. 打印将要 publish 的 topic、message summary、limit decision
6. 不创建或不使用 ROS command publisher 进行 publish
7. 机器人不应运动
```

`dry_run` 必须是默认值。没有显式配置时，executor 必须启动为 `dry_run`。

### 5.2 armed

真实 publish 模式。行为：

```text
1. 启动时打印醒目的 ARMED startup banner
2. 要求 CLI 参数和环境变量双确认
3. 只接受 packet.mode == "armed" 或明确约定的 active mode
4. 每个 packet 仍必须通过全部 safety checks
5. 通过检查后 publish ROS command topic
6. 任一安全条件失败时拒绝 publish，并记录 reason
```

建议双确认方式：

```text
CLI:
  --execution-mode armed
  --i-understand-this-publishes-robot-commands

environment:
  JZ_UDP_EXECUTOR_ARMED=1
```

如果 CLI 和环境变量没有同时满足，executor 必须降级为 `dry_run` 或直接拒绝启动；不要半隐式进入
`armed`。

### 5.3 packet mode 与 executor mode

executor mode 和 packet mode 都要参与门禁：

| executor mode | packet mode | 行为 |
| --- | --- | --- |
| `dry_run` | `dry_run` | 校验并打印，不 publish |
| `dry_run` | `armed` | 校验并打印，但不 publish；必须记录 executor 未 armed |
| `armed` | `dry_run` | 不 publish；记录 packet mode 非 active |
| `armed` | `armed` | 通过全部 safety gates 后才 publish |

这样可以避免只在 x86 或只在 Orin 单侧误配置就触发真实控制。

## 6. Safety Gates

Phase 3 的安全门禁是软件层必须实现的防线。用户会按急停做物理兜底，但急停不是软件安全机制的替代。
软件仍必须主动拒绝不可信、不新鲜、不连续、超限、过快或 schema 不匹配的 command。

### 6.1 sender IP gate

只接受配置中的 x86 IP。当前已验证网络信息：

```text
Orin IP: 192.168.1.81
x86 IP:  192.168.1.106
```

建议默认：

```text
bind_ip: 192.168.1.81
allowed_sender_ip: 192.168.1.106
command_port: 39020
```

不匹配 `allowed_sender_ip` 的 packet 必须丢弃，不进入 publish 路径。
armed 模式不允许把 `allowed_sender_ip` 配成空值、`None` 或 wildcard 地址；否则 sender IP gate 会失效，
executor 必须拒绝进入 armed。

### 6.2 mode gate

真实 publish 需要同时满足：

```text
executor execution_mode == armed
CLI armed acknowledgement present
JZ_UDP_EXECUTOR_ARMED == "1"
packet.mode == armed
```

任一条件不满足，只能 dry-run 或拒绝。

### 6.3 seq monotonic gate

`seq` 必须是整数并单调递增。

建议规则：

```text
first valid seq:
  accept and remember

next seq:
  accept only if seq > last_seq
  reject if seq <= last_seq
```

是否要求严格 `seq == last_seq + 1` 可作为配置项。第一版建议先使用 `seq > last_seq`，避免 UDP
偶发丢包导致 executor 进入不可恢复状态；但必须统计 gap：

```text
seq_gap_count += seq - last_seq - 1
```

### 6.4 stamp age gate

packet 必须带 `stamp_ns`，且不能太旧。

建议默认：

```text
max_command_age_s: 0.25
```

检查逻辑：

```text
age_s = now_ns - packet.stamp_ns
reject if age_s < -max_clock_skew_s
reject if age_s > max_command_age_s
```

建议同时提供：

```text
max_clock_skew_s: 1.0
```

如果 x86 和 Orin 没有可靠时钟同步，Phase 3 plan 应明确采用 `time.monotonic_ns()` 相对时间或在
dry-run 中先评估 stamp age 的实际分布，再 armed。不能在 armed 中完全关闭 stale command 检查。

### 6.5 command timeout gate

armed publish 后必须有 command timeout。超过一段时间没有收到有效 active command 时，executor
必须进入 inactive/stop 状态，并停止继续发布旧 command。

建议默认：

```text
command_timeout_s: 0.3
```

timeout 后行为：

```text
1. 标记 active=false
2. 不再重复 publish last command
3. 打印 COMMAND_TIMEOUT
4. 如实现 stop publish，只能发布明确设计过的 hold/stop message；不要随意构造未知安全姿态
```

对双臂位置控制，第一版建议 timeout 后“停止发布新 command”，不要自行发送零位置或随机 home
position。零位置不一定是安全姿态。

### 6.6 finite numeric gate

所有 command 数值必须是有限浮点数：

```text
reject NaN
reject +inf
reject -inf
reject non-numeric values
```

该检查覆盖：

```text
left/right joint position
left/right gripper width
left/right gripper force
```

### 6.7 joint count/name gate

双臂 command 必须各包含 7 个关节，并且名字完全匹配配置。

建议默认 joint names：

```text
left:
  left_joint1
  left_joint2
  left_joint3
  left_joint4
  left_joint5
  left_joint6
  left_joint7

right:
  right_joint1
  right_joint2
  right_joint3
  right_joint4
  right_joint5
  right_joint6
  right_joint7
```

如果 UDP packet `actions.left` / `actions.right` 是 dict，executor 必须按配置顺序提取 position，
不能依赖 JSON key 顺序。缺少、多出或拼错 joint name 都必须拒绝。

### 6.8 joint position absolute range gate

每个 joint 都必须有绝对位置范围限制。具体机械限位需要后续从机器人参数或实测安全范围确认；在未确认前，
Phase 3 plan 不应写死宽松到等同无限制的范围。

建议配置形式：

```yaml
joint_position_limits:
  left_joint1:  [-limit, limit]
  left_joint2:  [-limit, limit]
  ...
  right_joint7: [-limit, limit]
```

实现要求：

```text
1. armed 模式下必须加载 joint_position_limits
2. 任一 joint 缺少 limit 时拒绝进入 armed
3. 任一 position 超过 [min, max] 时拒绝 publish
4. dry_run 模式也应执行同样检查并打印 would_reject / would_accept
```

### 6.9 per-step delta limit gate

相邻有效 command 的 joint position 变化必须有限制，避免 UDP packet 或 action 生成错误导致突跳。

建议配置形式：

```yaml
max_joint_delta_per_step:
  default: 0.02
  overrides:
    left_joint1: 0.02
    right_joint1: 0.02
```

第一条 active command 的处理必须更保守：

```text
1. 如果 executor 可读取当前机器人 joint state，则第一条 command 也要与当前 state 比较 delta。
2. 如果读取不到当前 state，armed 模式不应接受第一条大幅 command。
3. 可以要求 first command 必须接近当前 observation 中的位置，或要求先 dry-run 预热后再 armed。
```

### 6.10 gripper range/force limit gate

夹爪 command 映射为：

```text
Float64MultiArray.data = [width, force]
```

必须限制：

```text
width_min <= width <= width_max
force_min <= force <= force_max
abs(width - last_width) <= max_width_delta_per_step
abs(force - last_force) <= max_force_delta_per_step
```

`max_width_delta_per_step` 和 `max_force_delta_per_step` 必须是保守的小值；armed 模式不允许用巨大但有限的
delta 值绕过夹爪单步变化限制。

probe 中看到的 sample：

```text
right gripper command sample: [0.0, 80.0]
gripper_status sample: [100.0, 6.0]
```

这些 sample 只能说明字段形态，不能单独定义安全范围。Phase 3 plan 需要把夹爪范围做成显式配置，
armed 模式缺少配置时拒绝启动。

### 6.11 publish rate limit gate

probe 观察到 VR command 约 72Hz，但 Phase 3 第一版不应直接追求高速控制。

建议第一版默认：

```text
max_publish_hz: 10
```

或与当前 `lerobot-record` dry-run 验证一致，先使用：

```text
record fps: 5
```

executor 必须限制 publish 频率：

```text
1. 如果 active packet 到达过快，按策略 drop 或 reject，并统计 rate_limited_count。
2. 不要为了追赶输入而 burst publish。
3. 日志中记录 accepted_hz / published_hz / dropped_by_rate_limit。
```

### 6.12 startup banner

启动日志必须清楚说明当前是否会 publish。

`dry_run` banner 必须包含：

```text
PHASE3 COMMAND EXECUTOR DRY-RUN
NOT publishing ROS command topics
robot should not move
bind_ip / port / allowed_sender_ip
configured topics
configured limits summary
```

`armed` banner 必须包含：

```text
PHASE3 COMMAND EXECUTOR ARMED
WILL publish ROS command topics
operator must be next to emergency stop
emergency stop is physical fallback, not a replacement for software limits
bind_ip / port / allowed_sender_ip
configured topics
configured limits summary
required acknowledgements present
```

### 6.13 kill/stop behavior

进程收到 `SIGINT` / `SIGTERM` 时：

```text
1. 立即停止接收循环或进入 shutdown
2. 不再 publish 新 command
3. 打印 summary
4. 关闭 ROS node / publishers
```

异常时：

```text
1. 不 publish fallback random command
2. 不发送零关节位置作为 stop
3. 不复用最后一条 command
4. 记录最后 accepted seq、published seq、reject reason 统计
```

如果后续要实现主动 stop message，必须先明确底层控制器对 stop/hold 的语义。没有明确语义前，Phase 3
第一版只做“停止发布新 command”。

### 7.2 双臂 JointState publish

左臂：

```text
topic:
  /robot1/telecon/arm_left/joint_commands_input
type:
  sensor_msgs/msg/JointState
name:
  ["left_joint1", ..., "left_joint7"]
position:
  [actions.left.left_joint1, ..., actions.left.left_joint7]
velocity:
  不填，除非后续明确设计
effort:
  不填
```

右臂：

```text
topic:
  /robot1/telecon/arm_right/joint_commands_input
type:
  sensor_msgs/msg/JointState
name:
  ["right_joint1", ..., "right_joint7"]
position:
  [actions.right.right_joint1, ..., actions.right.right_joint7]
velocity:
  不填，除非后续明确设计
effort:
  不填
```

说明：

```text
1. 不要因为 VR echo sample 中 velocity 有 7 值就自动填 velocity。
2. Phase 3 第一版只明确 position command。
3. 如果后续需要 velocity，必须补充 velocity 单位、limit、delta、timeout 和验收标准。
```

### 7.3 左右夹爪 publish

左夹爪：

```text
topic:
  /robot1/left_gripper/gripper_commands
type:
  std_msgs/msg/Float64MultiArray
data:
  [actions.grippers.left.width, actions.grippers.left.force]
```

右夹爪：

```text
topic:
  /robot1/right_gripper/gripper_commands
type:
  std_msgs/msg/Float64MultiArray
data:
  [actions.grippers.right.width, actions.grippers.right.force]
```

字段顺序必须与已有 `JZRobot.send_action()` 保持一致：

```text
[width, force]
```

不要改成 `[force, width]`，也不要把 `gripper_status` 的 sample 当成 command 的字段顺序来源。

## 8. 配置建议

Phase 3 executor 配置建议集中在一个 dataclass、YAML 或 argparse 结构中。后续 plan.md 决定具体落点时，
应保持这些字段显式可见。

网络：

```yaml
bind_ip: "192.168.1.81"
allowed_sender_ip: "192.168.1.106"
command_port: 39020
buffer_size: 65535
```

执行模式：

```yaml
execution_mode: "dry_run"  # dry_run | armed
require_env_armed: true
armed_env_var: "JZ_UDP_EXECUTOR_ARMED"
require_cli_ack: true
```

## 9. 验收标准

所有测试运行必须使用本仓库约定的 conda 环境。不得运行机器人相关命令，除非用户明确允许并且现场已准备急停。

### 9.1 Unit tests

覆盖：

```text
1. command packet decode
2. mode gate
3. sender IP gate
4. seq monotonic gate
5. stamp age gate
6. finite numeric gate
7. joint count/name gate
8. joint absolute range gate
9. per-step delta gate
10. gripper range/force gate
11. publish rate gate
12. dry_run 不调用 ROS publish
13. armed 条件不完整时不调用 ROS publish
14. armed 条件完整且 command 合法时才调用 ROS publish mock
```

Unit tests 不需要真实 ROS master 或机器人；ROS publisher 应使用 mock/fake。

### 9.2 Static safety tests

必须有静态测试防止危险默认值：

```text
1. 默认 execution_mode == dry_run
2. 默认不会 armed
3. 缺少 env var 不 armed
4. 缺少 CLI acknowledgement 不 armed
5. armed 缺少 joint limits 拒绝启动
6. armed 缺少 gripper limits 拒绝启动
7. cmd_vel topic 不存在于 Phase 3 executor publish path
8. Phase 2 receiver 不被无门禁改成默认执行
```

### 9.3 Dry-run regression

复测 Phase 2 链路：

```text
x86 JZRobotUDP.send_action()
  -> UDP command packet
  -> Orin receiver/executor dry_run
  -> log only
```

验收：

```text
1. 10s * 5fps = 50 command 仍可 dry-run PASS
2. Orin 侧收到 idx=50 seq=50 或等价连续统计
3. no publish
4. robot does not move
5. reject counters 为 0，除非测试刻意注入非法 command
```

### 9.4 Armed single small command test

这是第一步真实控制验收，只允许小幅单条 command。

前置条件：

```text
1. 用户明确允许真实控制
2. 人在机器人旁边
3. 手在急停附近
4. 软件 limit 已配置
5. executor startup banner 显示 ARMED
6. x86 packet mode 显式 armed
7. 不启用 policy inference
8. 不启用底盘
```

测试方式：

```text
1. 读取当前 observation
2. 构造相对当前 position 的极小 delta command
3. 只发 1 条或极少数 command
4. 验证 publish topic、seq、position、gripper data
5. 观察机器人实际动作是否符合预期
6. 出现异常立即 stop executor，必要时按急停
```

不要用全零 action 代替 single small command。全零并不等于“当前姿态附近的小 delta”，如果初始状态或
limit 配置错误，可能变成向零位目标运动；因此 armed single-small-command 的 x86 工具必须先读取
observation，再基于当前数值偏移一个明确的小 delta。

验收：

```text
1. 只 publish 双臂和夹爪 topic
2. 不 publish cmd_vel
3. command 通过全部 gate
4. 实际动作小且方向符合预期
5. timeout 后不继续重复 publish
```

### 9.5 Record active short episode

在 single small command 通过后，才允许短 episode active record。

建议第一版：

```text
duration_s: 5 to 10
fps: 5
max_publish_hz: 5 to 10
policy inference: disabled
base/cmd_vel: disabled
```

验收：

```text
1. record 可以完成
2. command seq 连续或 gap 可解释
3. publish_hz 在限制内
4. 无 stale command
5. 无 limit violation
6. 机器人旁边有人值守急停
7. 软件限幅仍开启
```

## 10. 明确不做

Phase 3 第一版明确不做：

```text
1. 默认真实执行
2. 底盘控制
3. publish /robot1/*/cmd_vel
4. 无门禁 publish
5. 使用急停替代软件限幅
6. 绕过 sender IP / mode / seq / stamp / limit checks
7. 大规模录制
8. policy inference 直接高速控制
9. 根据一次 probe sample 擅自定义完整机械限位
10. 训练数据质量判断
11. 修改 VR teleop 使其承担 Phase 3 executor 职责
```

## 11. 后续 plan.md 和代码实现注意事项

后续 `udp_test/docs/phase3/plan.md` 应先拆成可验证的小任务：

```text
1. 读取 Phase 1 / Phase 2 文档和本文档
2. 确认 Phase 2 command packet v1 当前实现
3. 设计 Orin executor 配置结构
4. 先写 safety gate unit tests
5. 写 fake ROS publisher 测试
6. 实现 dry_run executor
7. 做 Phase 2 dry-run regression
8. 加 armed 双确认逻辑
9. 加 ROS publisher mapping
10. 加 armed mock tests
11. 在用户明确允许后，再做实机 single small command
12. single small command 通过后，再做 record active short episode
```

代码实现注意事项：

```text
1. `udp_test/test_scripts/arm_side/orin_udp_command_receiver.py` 是 Phase 2 dry-run receiver，
   不能直接无门禁改成默认执行。
2. Phase 3 executor 可以复用 Phase 2 protocol decoder，但 publish 路径必须经过独立 safety gate。
3. ROS message schema 参考 `src/lerobot/robots/jz_robot/jz_robot.py`。
4. Topic/message schema 可参考 `src/lerobot/teleoperators/jz_command_teleop/`，但 executor
   应独立于 VR teleop。
5. armed 模式必须要求 CLI + env 双确认。
6. armed 模式必须要求 joint/gripper limits 完整配置。
7. 默认配置必须 dry_run。
8. 不要添加 cmd_vel publisher。
9. 不要填 JointState.velocity，除非后续文档明确设计。
10. 不要把 timeout stop 实现成发送零关节位置。
11. 日志要能区分 received / accepted / rejected / published / dry_run。
12. summary 要输出 received、invalid、rejected_by_gate、published、rate_limited、timeout、
    unexpected_sender、last_seq。
```

Phase 3 的核心结论：

```text
第一版只把 x86 UDP command 映射到 Orin 双臂 JointState 和左右夹爪 Float64MultiArray。
默认 dry_run。
真实 publish 必须 explicit armed，并且同时通过 sender、mode、seq、stamp、timeout、
finite numeric、joint name/count、joint range、delta、gripper limit、publish rate 等 safety gates。
急停是物理兜底，不是软件安全机制的替代。
```
