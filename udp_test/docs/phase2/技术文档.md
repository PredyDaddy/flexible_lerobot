# Phase 2 技术文档：JZRobotUDP Command Dry-run 链路

本文档记录第二阶段的目标、背景、边界和验收标准。第二阶段不是让机器人真实执行动作，而是把 `JZRobotUDP.send_action()` 到 Orin command receiver 的软件链路打通，并保持 Orin 端不发布任何 ROS 控制 topic。

## 1. 第一阶段完成内容和背景

第一阶段已经完成 `JZRobotUDP` 的 observation-only 链路：

```text
Orin / ARM:
  ROS2 state topic -> UDP state packet

x86:
  UDP state packet + RTSP camera -> JZRobotUDP.get_observation()
```

已固定并验证的网络信息：

```text
Orin IP: 192.168.1.81
x86 IP:  192.168.1.106
UDP state port: 39010
RTSP port: 8554
```

第一阶段已经完成：

```text
1. x86 侧新增 JZRobotUDP robot interface
2. Orin 侧新增 ROS -> UDP 只读状态桥
3. x86 能通过 get_observation() 读取 14 个双臂关节、4 个夹爪字段、3 路 RTSP 图像
4. server_bash/x86 和 server_bash/orin_arm 支持 start/stop/status 和日志查看
5. x86 + Orin 实机完成 OBS_COUNT=600 测试
6. 600 次 get_observation() 连续 PASS
```

第一阶段关键实测结果：

```text

camera_head  = 720x1280x3
camera_left  = 480x640x3

```

第一阶段明确没有做：

```text

UDP command packet
Orin command receiver
ROS command publisher
机器人真实控制
```

## 2. 做这个工作的意义

当前机器人主控是 Orin AGX。Orin 上保留 ROS2、机器人硬件 I/O、底层驱动和安全兜底。x86 侧承担 LeRobot、后续录制、推理、数据处理和调试。

这样拆分的主要意义是：

```text
1. 减少 Orin CPU/GPU/内存压力
2. 避免录制和推理把 Orin 上的 ROS/硬件通信挤占掉
3. 让 Orin 更像轻量机器人通信网关
4. 让 x86 负责更重的 LeRobot record、policy inference、数据编码和调试工具
5. 避免 x86 Ubuntu 24.04 上强行维护同版本 ROS2 / DDS 环境
```

第二阶段继续服务这个目标：让标准 LeRobot action path 可以先在 x86 上跑起来，但 Orin 端仍然不执行动作。这样可以提前验证 `lerobot-record`、`send_action()`、UDP command、Orin 解析和日志链路，减少后续真正进入控制阶段时的开发周期。

## 5. 第二阶段目标

第二阶段目标是实现 command dry-run 链路：

```text
x86 JZRobotUDP.send_action()
  -> action 校验
  -> UDP command packet 编码
  -> UDP 发送到 Orin
  -> Orin command receiver 接收
  -> sender IP / schema / seq / timestamp 校验
  -> Orin 打印 command 日志
  -> 到此为止，不 publish ROS command topic
```

第二阶段允许：

```text
1. 实现 JZRobotUDP.action_features
2. 实现 JZRobotUDP.send_action()
3. 实现 UDP command packet schema v1
4. x86 侧发送 command UDP packet
5. Orin 侧启动 command receiver
6. Orin 侧接收、解析、校验、打印 command
7. 标准 lerobot-record 可以调用 send_action 并继续录制流程
```

硬性定义：

```text
Phase 2 的 send_action() 只表示 LeRobot 接口层 dry-run：
  校验 action
  编码 command packet
  记录日志
  可选发送 UDP dry-run command packet 到 Orin

Phase 2 的 send_action() 不表示机器人 action 被启用。
Phase 2 不允许把 command 转成 ROS command、硬件控制或运动执行。
Phase 2 不允许加入 hidden active / armed / execute 参数。
```

第二阶段禁止：

```text
1. Orin publish ROS command topic
2. Orin publish cmd_vel
3. Orin 控制手臂
4. Orin 控制夹爪
5. 任何脚本默认让机器人动作
6. 把人工急停作为唯一安全措施
```

一句话边界：

```text
Phase 2 可以发 command packet，但 Orin 设计上永远不执行。
```

## 6. 第二阶段模式定义

### 模式 2A：x86 send_action local dry-run

用途：先验证 LeRobot action path 和 `JZRobotUDP.send_action()` 能被调用。

行为：

```text
send_action() 校验 action
send_action() 编码 command packet
send_action() 打印 DRY_RUN 日志
send_action() 不发 UDP
```

推荐配置语义：

```text
send_action_transport: local
send_action_execution: dry_run
```

验收：

```text
调用 send_action 不报 NotImplementedError
能看到 action key / seq / mode=dry_run 日志
没有 UDP command 发出
机器人不动
```

### 模式 2B：x86 UDP command -> Orin dry-run receiver

用途：验证 x86 到 Orin 的 command 网络链路。

行为：

```text
x86 send_action() 发 UDP command packet
Orin command receiver 收包
Orin 校验 sender/schema/seq/stamp
Orin 打印 DRY_RUN received command
Orin 不 publish ROS command topic
```

推荐配置语义：

```text
send_action_transport: udp
send_action_execution: dry_run
```

验收：

```text
x86 日志显示 sent command seq
Orin 日志显示 received command seq
seq 连续
无 parse error
无 stale command
无 unexpected sender
机器人不动
```

## 7. 推荐 command packet v1

第二阶段先使用 JSON，保持和第一阶段 state packet 一致，方便 tcpdump、日志和人工排查。

建议格式：

```json
{
  "version": 1,
  "type": "command",
  "robot": "robot1",
  "seq": 123,
  "stamp_ns": 123456789,
  "mode": "dry_run",
  "actions": {
    "left": {
      "left_joint1": 0.0,
      "left_joint2": 0.0,
      "left_joint3": 0.0,
      "left_joint4": 0.0,
      "left_joint5": 0.0,
      "left_joint6": 0.0,
      "left_joint7": 0.0
    },
    "right": {
      "right_joint1": 0.0,
      "right_joint2": 0.0,
      "right_joint3": 0.0,
      "right_joint4": 0.0,
      "right_joint5": 0.0,
      "right_joint6": 0.0,
      "right_joint7": 0.0
    },
    "grippers": {
      "left": {
        "width": 0.0,
        "force": 0.0
      },
      "right": {
        "width": 0.0,
        "force": 0.0
      }
    }
  }
}
```

第二阶段不要求这些 action 语义已经能驱动真实机器人。第二阶段只要求字段稳定、可校验、可记录、可通过 LeRobot action path。

### action_features 到 command packet 的映射

LeRobot `action_features` 可以沿用当前 observation 的 key 风格；UDP command packet 内部保持左右臂分组。映射规则必须显式实现，不能把 LeRobot key 原样塞进 UDP packet。

示例：

```text
left_left_joint1.pos   -> actions.left.left_joint1
left_left_joint2.pos   -> actions.left.left_joint2
...
right_right_joint1.pos -> actions.right.right_joint1
right_right_joint2.pos -> actions.right.right_joint2
...
left_gripper.width     -> actions.grippers.left.width
left_gripper.force     -> actions.grippers.left.force
right_gripper.width    -> actions.grippers.right.width
right_gripper.force    -> actions.grippers.right.force
```

## 8. lerobot-record 在第二阶段的语义

第二阶段完成后，允许开始使用标准 `lerobot-record` 做 dry-run 录制流程测试。

但必须明确：

```text
lerobot-record 会调用 robot.send_action()
Phase 2 的 send_action 只能 dry-run 或发到 Orin dry-run receiver
Orin 不执行 command
机器人不会按 action 运动
```

因此 Phase 2 的 record 数据适合验证：

```text
1. lerobot-record 能否启动
2. dataset 是否能创建和保存
3. observation 字段是否稳定
4. action 字段是否稳定
5. 三路图像是否写入
6. FPS 是否稳定
7. x86 send_action 日志和 Orin command receiver 日志是否对齐
```

不适合直接当成最终 imitation learning 训练数据，因为 action 没有真实执行，下一帧 observation 不反映 action 后果。

## 8.1 脚本层命令

### Orin command dry-run receiver

直接启动：

```bash
PYTHONPATH=src conda run --no-capture-output -n lerobot_flex python \
  udp_test/test_scripts/arm_side/orin_udp_command_receiver.py \
  --bind-ip 192.168.1.81 \
  --port 39020 \
  --allowed-sender-ip 192.168.1.106 \
  --count 0 \
  --print-every 1
```

通过 server_bash 启动：

```bash
AUTO_TAIL=1 bash udp_test/server_bash/orin_arm/start_command_receiver.sh
```

默认环境变量：

```text
ORIN_IP=192.168.1.81
X86_IP=192.168.1.106
COMMAND_PORT=39020
PYTHON_CMD="conda run --no-capture-output -n lerobot python"
AUTO_TAIL=1
```

停止和状态：

```bash
bash udp_test/server_bash/orin_arm/stop_command_receiver.sh
bash udp_test/server_bash/orin_arm/status.sh
```

receiver 启动时必须打印：

```text
PHASE2 COMMAND DRY-RUN ONLY
NOT publishing ROS command topics
robot will not move
```

### x86 send_action check

local dry-run：

```bash
PYTHONPATH=src conda run --no-capture-output -n lerobot_flex python \
  udp_test/test_scripts/x86_side/x86_jz_robot_udp_send_action_check.py \
  --robot-config src/lerobot/configs/robot/jz_robot_udp_three_rtsp.yaml \
  --transport local \
  --execution dry_run \
  --command-only \
  --count 20 \
  --hz 5
```

x86 -> Orin UDP dry-run：

```bash
PYTHONPATH=src conda run --no-capture-output -n lerobot_flex python \
  udp_test/test_scripts/x86_side/x86_jz_robot_udp_send_action_check.py \
  --robot-config src/lerobot/configs/robot/jz_robot_udp_three_rtsp.yaml \
  --transport udp \
  --execution dry_run \
  --command-only \
  --command-target-ip 192.168.1.81 \
  --command-target-port 39020 \
  --count 20 \
  --hz 5
```

`--command-only` 是默认模式，只测试 command protocol 和 `send_action()` path，不连接 RTSP 相机，不等待 fresh state。它只会为了通过 LeRobot Robot 接口的 connected 检查设置最小连接标志，不启动任何相机或机器人控制链路。

### 本机 127.0.0.1 dry-run

终端 1：

```bash
PYTHONPATH=src conda run --no-capture-output -n lerobot_flex python \
  udp_test/test_scripts/arm_side/orin_udp_command_receiver.py \
  --bind-ip 127.0.0.1 \
  --port 39020 \
  --allowed-sender-ip 127.0.0.1 \
  --count 20
```

终端 2：

```bash
PYTHONPATH=src conda run --no-capture-output -n lerobot_flex python \
  udp_test/test_scripts/x86_side/x86_jz_robot_udp_send_action_check.py \
  --robot-config src/lerobot/configs/robot/jz_robot_udp_three_rtsp.yaml \
  --transport udp \
  --execution dry_run \
  --command-only \
  --command-target-ip 127.0.0.1 \
  --command-target-port 39020 \
  --count 20 \
  --hz 5
```

预期摘要格式：

```text
x86: SUMMARY: PASS commands=20
receiver: SUMMARY: received=20 invalid=0 unexpected_sender=0
```

如果核心 command protocol helper 或 `JZRobotUDP.send_action()` 还没有合入，脚本会在运行时明确报缺失接口或 action_features 为空；脚本层不会退化为任何真实机器人控制。

### lerobot-record dry-run caveat

`lerobot-record` dry-run 必须使用本地 dataset、`push_to_hub=false` 和安全的 dry-run action source。Orin 端仍只运行 command dry-run receiver，不 publish ROS command topic，不 publish `cmd_vel`，不控制手臂或夹爪。人工急停是最后兜底，不是 Phase 2 的主要软件安全机制。

## 9. 第二阶段验收标准

第二阶段完成必须同时满足以下条件。

### 9.1 安全验收

```text
[必须] Orin command receiver 不 create_publisher
[必须] Orin command receiver 不 publish ROS command topic
[必须] Orin command receiver 不 publish cmd_vel
[必须] Orin command receiver 不调用任何机器人控制 API
[必须] 所有启动脚本默认 dry-run
[必须] 日志明确写出 DRY_RUN / NOT publishing
[必须] send_action 默认不能绕过 dry-run 安全门
```

### 9.2 协议验收

```text
[必须] command packet version/type 校验
[必须] command packet robot 字段校验
[必须] command packet seq 单调递增或可检测乱序
[必须] command packet stamp_ns 存在
[必须] command packet actions 字段完整
[必须] 无效 packet 被拒绝并打印原因
[必须] unexpected sender IP 被拒绝
```

### 9.3 x86 send_action 验收

```text
[必须] JZRobotUDP.action_features 非空
[必须] JZRobotUDP.send_action() 不再抛 NotImplementedError
[必须] local dry-run 模式不发 UDP
[必须] udp dry-run 模式能发 UDP command 到 Orin
[必须] send_action 日志包含 seq、mode、action key 数量
[必须] send_action 返回值符合 LeRobot Robot 接口预期
[必须] Phase 2 配置里不得出现 active / execute / armed 真实执行模式
```

### 9.4 Orin receiver 验收

```text
[必须] Orin command receiver 能 bind 192.168.1.81:39020
[必须] 只接受 x86 192.168.1.106 的 command
[允许] 本机测试可通过显式参数使用 127.0.0.1，但实机默认不能用 127.0.0.1
[必须] 能连续接收并打印 command seq
[必须] 遇到 SIGINT/SIGTERM 能干净退出
[必须] start/stop/status 脚本可用
[必须] stop 后无残留 command receiver 进程
```

### 9.5 LeRobot record dry-run 验收

```text
[必须] 标准 lerobot-record 能完成一个短 episode dry-run
[必须] dataset 仅作为流程工件保存 episode，不 push hub，不作为最终训练数据
[必须] dataset features 同时包含 observation 和 action
[必须] x86 record 期间无 send_action NotImplementedError
[必须] Orin command receiver 日志能看到对应 command
[必须] 机器人不动
```

建议第一版验收参数：

```text
episode_time_s: 10
num_episodes: 1
fps: 5 或 10
push_to_hub: false
video: true
```

### 9.6 回归验收

第二阶段不能破坏第一阶段 observation 链路。

必须重新通过：

x86 上先执行：

```bash
OBS_COUNT=600 bash udp_test/server_bash/x86/start.sh
```

Orin 上后执行：

```bash
bash udp_test/server_bash/orin_arm/start.sh
```

预期：

```text
SUMMARY: PASS observations=600
keys=21 numeric=18
三路 image_shapes 正常
无 stale_count / TimeoutError / traceback
```
